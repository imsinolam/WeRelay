# 桌面完成通知与微信发送恢复

## 两种故障不能混为一谈

“任务已完成，但微信没有通知”必须按以下三段分别核验：

1. **真实 Agent 已完成**：原生历史有终态和同一轮最终回复，不能用目录更新时间、改名或工具记录代替。
2. **WeRelay 已捕获**：完成通知已进入私有、持久化的投递队列。
3. **微信已接收**：文本及附件完整发送成功，队列才记为 delivered。后台在线、轮询恢复、HTTP 请求开始都不是送达证据。

空闲启动允许 `slots` 为空。此前 Codex 的完成监控只随 Codex slot 建立，WorkBuddy 的实时 final reply 又只覆盖桥接自身发起的运行；因此桌面自行执行的任务可能从未进入第二段。不能通过自动打开应用、恢复最近任务或新建隐藏会话来“补监控”。

## 独立于 owner 的只读补捕获

`PassiveCompletionMonitor` 随微信 daemon 轮询启动，不依赖当前终端或已连接 slot：

- 初次立即扫描，之后每 30 秒扫描；同一监控只有一轮在途。
- 当前只读来源为 **Codex、WorkBuddy**。其他终端保留原有事件监听；不宣称所有终端已经拥有相同的历史补捕获能力。
- 每个来源读取最近 100 个会话，只补现有 6 小时投递窗口内、能证实的最近完成轮次。不是历史全量重放；极高频会话或扫描期间连续完成多轮仍需依靠原生实时事件。
- SQLite、历史尾读、图片路径解析在按终端隔离的 worker 内执行，15 秒超时，空闲释放。不能把同步目录/历史扫描移回 daemon 主线程，以免拖慢微信入站或其他终端心跳。
- WorkBuddy 尾读上限 2 MiB；通常用最近用户消息和同轮 completed 回复证明完成。用户记录落在尾读范围外时，只接受数据库完成时间与原生终态回复时间**精确一致**的证据，不猜测开始时间或耗时。
- Codex 使用有界原生尾读：最近 task boundary 必须是 completed，最终文本来自该 turn 的原生 `task_complete.last_agent_message` 或同 turn 的 final answer。running、失败、取消、新用户消息和旧轮回复不能误报为当前完成。
- 不创建 runtime、不调用桌面 IPC、不启动/重启应用、不切换当前任务、不建立独立 CLI owner。

捕获后先格式化并持久化，再触发已有后台投递恢复；网络与微信上下文拒绝不得阻塞历史扫描或入站轮询。读取失败下轮重试；单终端失败不影响其他终端。

## 统一去重与路由

- Codex 保留既有 `sessionId:turnId` 投递身份，与实时完成事件共享队列。
- WorkBuddy 使用原生最终消息 ID，实时 final reply 的 `messageId` 与历史恢复使用同一生成规则；不能以事件到达时间作为稳定完成身份。
- 身份包含终端与会话，跨终端相同 sessionId 不互相覆盖。
- 通知捕获不会改变微信“直接回复”目标；完整送达后才更新回复目标。任务序号来自同一全局快照，链接仍使用已有短链发送链路。
- 队列持久化文本、附件和部分发送游标，重启后继续未送部分；完整送达后去重。

已有 WorkBuddy 通知如果只有“到达时间 + 文本”散列、没有原生消息 ID（例如旧版本，或实时回复到达时历史尚未落盘），不能可靠反推旧 ID；格式交界处可能出现窗口内的一次补通知，不能为消除这种可能性而把未送通知视为已送。

## 微信发送失败的安全边界

`ContextSendGuard` 在真正发送前写入私有 write-ahead 标记：

| 证据 | 处理 |
| --- | --- |
| 明确 `prepare failed` 上下文拒绝 | 保存拒绝/退避状态，不伪造新 token；新微信入站刷新上下文可触发恢复 |
| 结构化错误链中的 `ENOTFOUND` / `EAI_AGAIN` | DNS 解析发生在 HTTP 发送之前，仅移除本请求的在途标记，交给恢复队列安全重试 |
| 超时、连接重置、未知错误 | 送达结果不明，保留 uncertain 保护，不使用 DNS 的确定未发送重试路径 |
| 重启时仍有在途标记 | 按现有 uncertain 恢复规则处理，不清空全部保护状态 |

不能用错误文本含有 DNS 关键字作为依据；不能把 `ECONNRESET` 或超时纳入确定未发送；不能因某一请求失败清除其他收件范围或请求的保护状态。

退避、未确认标记的既有过期/刷新规则及端到端限制，以[微信发送上下文与送达恢复](微信发送上下文与送达恢复.md)为准；本次不改变这些过期规则。

6 小时过期策略不变。已过期通知不无限重放；恢复连接也不等于过期历史会自动补齐。排查必须区分“从未捕获”“待送/部分已送”“已完整送达”“已过期”。

## 防回归验收

- `test/daemon/passive-completion-monitor.test.ts`：空闲无 slot 捕获、跨终端同 ID、失败重试、停止/单轮执行、持久化恢复、成功去重、旧轮证据过滤。
- `test/daemon/desktop-completion-catalog.test.ts`：隔离临时数据库和真实 Node worker，完成历史进入 daemon 持久化队列；不连接 owner、不发真实网络、不改变回复目标；新用户/运行轮次屏蔽旧回复。
- `test/bridge/bridge-adapters.workbuddy.test.ts`：原生终态、消息 ID、长轮次数据库时间证据和实时通知身份。
- `test/daemon/final-reply-delivery.test.ts`：实时/历史去重与文本、附件的独立 checkpoint。
- `test/wechat/context-send-guard.test.ts`：DNS 可重试、未知结果仍受保护、重启与上下文刷新。

真实验收仍需在同一候选安装后完成：保持 daemon 空闲、不从微信选择终端，在电脑端分别完成 WorkBuddy/Codex 原任务；确认微信收到带序号和链接的结果，重复扫描/重启不重复。遇到上下文拒绝，应从微信发送新消息刷新上下文后再验活，不能以 mock 测试声称真实送达。
