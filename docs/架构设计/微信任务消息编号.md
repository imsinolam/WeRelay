# 微信任务消息编号契约

## 展示规则

归属于明确任务的文本消息，开头必须使用全局任务快照中的真实编号：

```text
[任务 12 · Pi · 排查模型连接]
任务结果……

https://relay.example/short-link
```

Codex 保留现有简洁标题，如 `[任务 12 · 排查模型连接]`；其他终端增加终端名。Pi 推送统一简写为 Pi。数字必须可用于“任务12：内容”，不能是汇总内部另起的展示序号，也不能用截断的会话 ID 冒充。

系统连接状态、终端切换失败、使用说明等不属于某条真实任务，不强行分配编号。

## 原因与修复边界

- 非 Codex 的旧任务格式化函数接收编号却未显示；现统一加任务编号。
- 请求全文的格式化函数也遗漏传入编号；取编号改用全局索引，不依赖终端自身的局部编号。
- Codex 长结论在拼接头部后切块，后续消息失去归属；各段重复任务身份，并为标题预留文本长度。
- 网页消息投递失败通知原先自行拼任务名，绕开全局索引；现注册原任务并通过同一编号入口输出。
- 持久待补发 payload 可能在旧版生成，或生成后用户刷新了编号。发送时按 adapter + sessionId 重新解析当前编号，替换可识别的旧路由头，不改变投递 key、已送分段 checkpoint 或原任务身份，不重复发送已送片段。
- 锁屏即时推送、解锁汇总、积压完成汇总、审批补发均使用这个编号入口；汇总不另设假序号。
- 单会话型终端的失败/中断事件可能没有 threadId，使用事件处理时捕获的真实会话身份。不能等异步发送时再取已切换的新任务。没有确定身份的系统消息不猜任务。

编号的稳定范围仍是现有全局快照：下一次裸“任务”可以刷新排序和编号；终端筛选只筛选同一个快照。旧微信消息不会被修改，延迟补发使用发送时的当前编号。不同 adapter 相同 sessionId 必须拥有不同编号。

## 防回归

`test/daemon/task-message-number.test.ts` 覆盖全终端标题、全文和预览各段、旧队列重启及部分已送、旧编号刷新、跨终端同 ID、审批、汇总、网页失败和无 threadId 的单会话失败。

更改通知策略或增加 adapter 时，不能重新写一个只带任务名的通知头；走统一任务格式化及投递入口。部署后需验收正常完成、审批、长回复后续段及补发消息，确认数字直发继续同一任务。
