# 公网 WebSocket 设备通道

## 目标与边界

电脑主动连接公网 Relay，优先使用 WSS；升级不支持或连接失败时串行回退到 HTTPS 长轮询。网页继续使用已有 HTTPS API，微信 iLink 不变。本通道只承载 WeRelay 的受限任务 API，不提供任意端口、URL 或终端转发。

开发基线为现行已验活的 WeRelay 0.3.16。此文同时记录本轮实施计划，不表示已经部署到公网。

## 协议与安全

- 独立设备路径 `/__werelay/device/ws`；握手通过请求头携带设备身份与 Bearer 认证，禁止 URL 中携带密钥，拒绝带 Origin 的浏览器连接。
- WebSocket 消息采用版本化 JSON 信封：欢迎、就绪容量、指令、响应、响应确认、心跳及心跳确认。业务指令与长轮询复用相同协议、编号、截止时间及持久化写操作结果。
- 公网使用 WSS、校验证书；明文 WS 仅供回环测试。尊重 HTTP/HTTPS 代理与 NO_PROXY，不关闭 TLS 校验。
- 关闭压缩、限制帧大小、限制并发及写缓冲。连接无效、格式错误或心跳超时就关闭；日志不包含认证数据和业务正文。
- 同一设备只有一个有效 WebSocket owner；新连接替换旧连接。WSS 活跃期间 HTTP poll 被拒绝，HTTP 心跳与结果回传仍可用。

## 恢复与防重复

客户端最多接受八条在途指令，写操作串行。服务端按客户端报告的剩余容量发送，指令使用原有租约与过期机制；断线不创造新指令 ID。

结果收到服务端确认才认为传输完成。断线时可通过原 HTTP respond 补交结果；已完成写操作重复投递时读取原有结果记录，不再次执行。重连仍使用同一份在途集合和日志。不能据此承诺端到端绝对一次执行：进程在实际执行与记录结果之间崩溃仍有原有不确定性。

WSS 尝试有明确握手与心跳截止时间。失败后先运行一段长轮询，再重新尝试 WSS；不同时开启两个指令消费循环。服务端业务繁忙不阻止心跳；电脑睡眠或网络半断开由心跳截止时间发现。

## 实施顺序

1. 添加协议常量、受限 WebSocket 客户端连接与认证握手。
2. 服务端复用原指令队列，加入单 owner、容量、心跳、响应确认及资源清理。
3. 客户端复用执行器与结果记录，加入 auto/long-poll 模式及有界回退。
4. 更新反向代理模板、配置入口和使用文档。
5. 自动验收：真实回环 WS 收发、错误认证、Origin、连接替换、超时/断线、回退旧服务、租约重投去重、并发及关闭。
6. 隐私、lint、类型检查、完整测试、构建、打包后提交。公网 TLS、代理和睡眠恢复在后续用户授权的体验部署中验收，不在开发阶段重启生产服务。

## 部署与回滚

先升级 Relay 并配置 Nginx Upgrade，再升级电脑；旧电脑继续长轮询，新电脑面对旧 Relay 会回退。可将电脑 `WERELAY_RELAY_TRANSPORT` 设为 `long-poll` 恢复旧通道；仍由发布负责人打包同一产物、串行部署并验活。不会改变原任务 owner、版本号或设备配对。
