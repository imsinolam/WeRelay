# 微信出站拒绝与恢复

## 判断边界

`sendmessage` 的负返回值说明请求未正常完成，不能单凭 `ret=-2` 就证明上下文过期，也不能推导固定有效期。自动恢复仅处理明确的 `prepare failed` 拒绝；其他返回、超时、断连及未知结果采取保守暂停，避免重复发送。服务器在线、Agent 已回复与微信送达是三个独立状态。

## 发送与持久化

- 所有正文、图片、文件、语音、视频的最终消息提交共用发送保护。媒体上传结束后才取当前上下文；请求使用旧上下文且被明确拒绝时，仅在已有新上下文的情况下再试一次。
- 每一次实际发送（包括旧请求失败后改用新上下文补试）都重新检查当前上下文的退避与熔断状态；晚返回的旧请求不能绕过或改写新上下文保护。
- 明确拒绝时，在同一个原子快照中写入拒绝次数并解除本次请求的未确认标记。重启只能读到发送中或最终拒绝状态，不存在同时丢失两者的中间状态。
- 不再因单项失败删除整个收件人的上下文。拒绝状态按账号、收件人及上下文的不可逆指纹隔离，不保存明文凭据或正文。
- 同一上下文明确拒绝后按 1 分钟、5 分钟退避，累计 3 次拒绝后暂停，等待新的上下文。恢复记录存入私有的 `context-send-recovery.json`，重启不会重置次数。后台检查每分钟有一次机会，实际节奏受长轮询结束时间影响。
- 请求前先写未确认标记，成功或明确拒绝后解除。进程在发送中退出、网络失败或结果未知时，重启也不会盲目重发。图片使用内容指纹，而不是每次上传产生的新密文地址作为未确认请求身份。
- Codex 完成通知逐项持久保存正文/链接发送位置和图片发送位置；全部完成才标记通知送达。图片未送达的通知不纳入会丢弃原始分片的积压摘要确认。
- 入站消息仍先锁定任务目标，再恢复出站；补发不能改投已收到的用户输入。

## 限制与维护

这是本地发送与恢复策略修复，不是上游拒绝原因的证明，也不保证客户端能自行生成上游认可的新上下文。次数耗尽后需要新的有效上下文；结果未确认则应人工核实微信收件结果，不能通过重启绕过保护。当前未提供自动消除未确认记录的命令或界面。

旧版本已经错误标记送达的图片没有持久待发送记录，升级不能自动找回这些历史缺项。正文与图片写入本地检查点仍不能提供端到端 exactly-once：请求期间的崩溃会保守暂停，宁可要求核实，也不重复发送。当前完整图片检查点覆盖 Codex 完成通知，其他入口的附件和带 caption 的独立媒体调用仍需分别审查。

恢复记录最多保留 500 个收件范围的拒绝状态及 500 个未确认内容指纹；未确认记录满时停止新自动发送而非淘汰后冒险重发。不要记录或分享原始账号、上下文 token、真实运行文件。
