# 锁屏感知任务通知

## 产品规则

只限制主动的任务完成和执行审批通知，不限制用户发送指令后的回复。

| 电脑状态 | 主动通知 |
| --- | --- |
| 锁屏 | 每次完成、每项审批分别推送，不应用积压摘要策略 |
| 未锁屏 | 第一次可立即发送摘要；之后两次成功推送至少间隔 10 分钟，期间内容合并 |
| 无法确定 | 按即时通知处理，避免检测失败让审批静默卡住 |

微信入站消息刷新上下文后仍遵守以上规则。用户主动查询任务、进入任务、回复审批不必等十分钟。解锁期间的审批可能最多等待十分钟，这是用户选择的降打扰行为；不擅自为审批开例外。锁屏不会唤醒睡眠电脑，电脑离线或睡眠期间不能发通知。

macOS 使用系统会话的锁屏标记，不以屏保、应用前后台或屏幕亮灭猜测。检测有超时和输出大小上限，不保存系统原始输出。多用户标记矛盾时返回未知。尚未实现其他平台的系统探针，统一按未知处理。

## 队列与送达

- 原有完成、审批持久化队列是唯一 payload 来源，不另建一份可能丢失的内存摘要队列。
- 只在微信确认整条发送成功后确认摘要条目并更新最近主动推送时间；失败保留 payload，下轮或新上下文补发。
- 最近成功推送时间写入私有 daemon state，重启不重置十分钟间隔。
- 摘要跨 Agent 合并，保留任务标题、任务序号（正文已有时）及任务链接。审批在前，完成在后；单条最多 8 项、1600 字符，剩余条目留到后续窗口。
- 有任务链接的完成摘要以网页引用代替内联图片和附件，原结果仍在原任务中；无链接的媒体结果不能假定已交付，继续保留等待即时投递。
- 审批在投递前校验是否仍待确认；已解决的不再通知。WorkBuddy 审批在无事件接口、无法确认时保留，不将未知当成已解决或仍待审批。
- 摘要和完整投递共用队列 in-flight 预约，屏幕状态变化不能把同一条内容同时送两遍。
- 既有完成六小时投递窗口、队列上限、微信上下文拒绝与未知送达保护均保留。网络恢复或成功轮询不等于已送达；锁屏政策不能绕过这些保护。
- 微信与本地磁盘不是分布式事务；微信已接受、但进程在保存确认前崩溃的极小窗口仍无法承诺严格 exactly-once。

## WorkBuddy 审批与完成不是同一条链路

完成可以从只读 SQLite 和最终消息历史补查；审批必须有原生的未决请求标识和可操作事件接口。仅看到数据库 working、工具记录或审批字样不能合成审批，也不能据此自动允许。

已有桌面接口时，daemon 可创建通知观察连接：只连接已有接口、只读 session:list / session:get、接收权限事件，不调用 session:load、sendMessage、create，不打开或重启应用，不设置 activeAdapter，不创建新 owner。

已连接的 WorkBuddy 对所有会话处理权限事件，身份为 sessionId + requestId；文本输出仍按当前会话过滤。快照补查缺失的权限事件，只把明确的 pendingPermissions 空列表当成解决，未知字段或失败保持原状态。不同会话中相同 requestId 不能冲突。非当前任务的审批不能阻挡当前任务输入。

如果接口尚未开放：读取历史依然可用，但无法声称实时审批已接入。通知观察器不回退到独立 ACP owner，也不擅自重启应用装载 Hook；应说明缺失的接入条件，由用户明确允许后在安全时机接入。已经运行中的任务不得被自动替换。

## 防回归验收

1. 空闲 daemon 接到非当前 WorkBuddy 会话权限事件，网页和微信队列都出现同一请求；没有桌面加载、新任务或应用启动调用。
2. 丢失事件后由原生快照补回，重复事件去重；另一会话同 requestId 独立；已解决快照撤销。
3. 锁屏连续三项完成分别发送；未锁屏多终端完成和审批只发一条摘要。
4. 摘要发送失败、未知结果或 daemon 重启，payload 不丢失；成功后十分钟以内不再主动推送。
5. 未锁屏等待期间进入锁屏，下个恢复周期逐条补发；无任务链接的媒体不提前确认送达。
6. 用户命令即时回复；无 activeAdapter 时也可用审批快捷数字回应观察连接里的请求。

部署验收必须使用正在运行的真实 WorkBuddy/Codex 原任务、真实微信上下文，分别实测锁屏与解锁。模拟测试和开发提交不能替代实机送达结论。
