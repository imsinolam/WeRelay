# Pi 原生会话与桌面复用

## 故障原因

旧 daemon 将 Pi 交给 companion 代理。读取任务列表必须等 companion 内的 Pi 扩展发布 ready；daemon 启动目录没有匹配连接时，还可能打开一个空窗口。用户在其他项目运行原任务，不能保证这个新窗口就绪，因此出现“Pi 在运行，但 /pi 无法读取任务”。这是目录读取与写者连接的职责混淆，不能靠反复重启 Pi 解决。

旧原生索引只查看一级项目桶，并依赖文件名寻找任务；忽略配置的 agent 目录。桌面可以递归读取、更名或复用原文件，造成目录内容与任务身份不一致。文件修改时间也会受复制影响，不能代表实际会话更新。

Pi Desktop 的原生显示 ID 是 `native-pi:` 加原文件真实路径、NUL 和原生 ID 的 SHA-256 base64url 前 24 位。它是别名，不是另一条会话。旧扩展以 PID 命名连接文件，一个桌面 sidecar 承载多个原生运行实例时会冲突。

## 本次修复的契约

1. daemon Pi slot 启动空闲目录读取器，不启动 TUI。取列表和历史不依赖 writer ready；显式 `werelay-pi-start` 的可见终端入口保留。
2. 原生 ID 是集合的统一身份；同 ID 文件去重，按实际记录时间排序。递归深度、文件数和同时打开文件数有上限，不跟随目录符号链接。
3. 列表筛选不附着任意“最近 owner”。选择或发送才发现匹配原生 ID 的唯一、当前用户、存活、私有且经 token 验证的 owner。桌面别名只经路径与原生 ID 计算验证后解析。
4. 每个扩展实例使用 PID 加随机后缀的独立广告及 socket，兼容旧 PID 文件。项目用扩展上下文 cwd；运行/完成时更新状态。关闭一个扩展只清理自己的广告及连接。
5. 相同 ID 的多个 owner 拒绝发送，不选第一个。同一 ID 的重连操作串行化；恢复状态中的相同 ID 尚未连上或已断开时，发送重新认证原任务，而不是直接报未连接。
6. daemon 断开 owner 后列表仍可读，不关闭整个 Pi slot。模型读取未连接时说明能力不可用；修改模型或强度时重新确认原任务。真实 owner 完成状态不因发送确认稍晚到达而回到忙碌。
7. 附着原进程不是创建 writer，不争抢管理终端的启动锁。显式启动不得抢占 Pi Desktop 的原生 lease，不删除桌面锁、不启动替代 CLI、不改写原历史。

## 支持边界

Pi CLI 与 Pi Desktop **复用原生记录**属于同一个 Pi 集合。Desktop 原生运行实例须加载 WeRelay 扩展，目录可见不等于已具备发送能力。旧扩展升级后需要在原 CLI `/reload`；桌面需让原生运行实例重新加载扩展，不由 WeRelay 强制重启应用。

Pi Desktop 自建的独立桌面会话有另外的数据库、JSONL 格式及写者协议，本修复未实现它们的索引或发送。不能宣称“所有 Desktop 自建任务都已接入”，也不能启动新 sidecar 冒充已有 writer。Windows 暂不支持普通原窗口的 POSIX owner 发现。

## 防回归验收

- `pi-integration.test.ts`：没有 ready 仍能取任务和历史，不写文件、不启动进程；全局目录保留项目身份。
- `pi-session-catalog.test.ts`：根目录、递归、更名、重复 ID、agent 目录、真实记录排序、桌面别名及符号链接边界。
- `pi-existing-owner.test.ts`：既有认证原窗口发送；同 ID 首次发送/断线恢复；一个 sidecar 多任务各自路由；重载不删除其他广告；owner 冲突拒绝；并发同任务只建立一个连接。
- `pi-owner-safety.test.ts`：无接口拒绝新 writer；Desktop lease 不删除；项目创建不串项目；完成先于确认不回到忙碌。
- `werelay-daemon.test.ts`：识别 Pi Desktop 为 Pi；`/pi` 不触发打开可见空终端。

部署后还必须实际验收：保持已有 CLI/Desktop 任务，微信 `/pi` 返回统一列表，分别向指定原任务发一次消息，在原窗口确认只有一条新用户消息和一个真实运行轮次。无接口任务应明确报错而非分叉。模拟扩展与只读目录验证不能代替这项微信端验收。
