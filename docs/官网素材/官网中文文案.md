## Hero

**本地 AI Agent 的移动任务接力层**

# 离开电脑，继续同一条 AI 编程任务

很多 Agent 接上手机后，只是多了一个下指令的新窗口：看不到电脑上的任务列表，也回不到原任务。WeRelay 把微信 ClawBot、局域网网页和公网网页接入电脑上真实运行的 Codex、WorkBuddy、Grok、Claude Code、DeepSeek Harness 等 Agent，让你从手机找到原任务，继续验收、审查和派活——不另开会话，不复制上下文。

## 核心痛点：手机新窗口不等于移动化

手机上能发送一句指令，只解决了“远程输入”。如果移动端不能读取电脑 Agent 的原有任务列表，不能进入原任务查看历史和进度，也不能围绕原结果继续验收、审查和派活，那么它仍然是一条独立的新会话，移动化的意义并没有成立。

真正的移动接力应该形成完整闭环：

1. **找到原任务：** 读取电脑 Agent 已经存在的任务列表；
2. **接上上下文：** 进入原任务，了解它做到了哪里；
3. **验收与审查：** 查看结果、过程、审批和风险；
4. **继续派活：** 把修改意见和下一步要求发回同一任务。

重点句：

> **移动化的单位不是消息，而是任务。**

> **手机端多一个输入框，不叫移动化；能回到原任务，才叫接力。**

> **从电脑开工，在手机验收，再把下一步派回同一条任务。**

## 核心证明

### 电脑端是唯一 owner

Agent、任务上下文、项目文件、模型和工具权限始终由电脑端真实 Agent 持有。

### 手机接力的是完整任务，不只是下一条消息

微信和网页读取电脑 Agent 的真实任务列表。用户进入原任务后，可以查看上下文和运行状态，验收结果、审查过程、处理审批、停止错误方向并继续派活，而不会生成另一套隐藏聊天记录。

### 不可用时明确离线

电脑离线或真实 Agent 无法继续时，WeRelay 会清楚说明原因，不会悄悄切换到独立 CLI/ACP 会话。

## 四类对象的关系

| 对象 | 首页应如何解释 |
| --- | --- |
| Codex / WorkBuddy / Grok / DeepSeek Harness 等电脑 Agent | 真实任务、上下文和工具的 owner |
| WeRelay | 负责映射真实任务与可靠传输，不是新的 Agent |
| 微信 ClawBot | 轻量远程入口和完成通知入口 |
| 局域网网页 | 同网时直接访问电脑，速度更快 |
| 公网网页 | 通过用户自建 Relay 访问同一任务 |

公网模式必须明确：Mac 主动通过 HTTPS 连接 Relay，服务器不反向连接 Mac，不暴露本机通用端口，不运行另一份 Agent。

## 网络模式文案

### 没有服务器

微信 ClawBot 仍可远程使用，因为连接由电脑主动发起；移动网页只在手机与电脑处于同一可互访局域网时可用。

### 有公网服务器

公网网页连接 HTTPS Relay，Mac 主动取回 WeRelay 任务请求并返回结果。Relay 只传输消息、状态、审批和附件，不提供任意 TCP/HTTP 转发。

## 安全边界文案

- 不直接暴露本机端口；
- 不把 Relay 做成通用代理；
- 设备与 Relay 使用独立长随机密钥；
- 登录、任务、日志和附件不应出现在公开截图或仓库；
- 电脑端 Agent 的权限和审批仍然生效。

## 视觉建议

- 使用真实、脱敏的双端产品截图，不用抽象手机模型代替；
- 产品演示必须先展示“读取电脑端原任务列表”，不能只展示手机聊天框；
- 至少展示一次“进入原任务 → 验收结果 → 继续派活”的完整接力过程；
- 首屏只保留一个强主按钮；
- 避免大段终端代码，安装只展示一行；
- 用一张清晰关系图解释数据流；
- 强调“同一条任务”和“移动接力”，不要把产品描述成聊天机器人集合。
