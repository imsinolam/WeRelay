# 第二阶段：GitHub 正式发布操作手册

本文只用于执行两阶段流程的第二阶段。开发完成后应先按[体验部署与正式发布](体验部署与正式发布.md)创建体验候选、部署本机和公网 Relay，并经过用户认可的真实使用观察。**只有用户明确要求发布 GitHub 新版本后，才能执行本文。**

WeRelay 可能由多个 Agent 并行修改，但一次 GitHub 正式版本只能由一个用户明确指定的正式发布 Agent 负责。普通开发 Agent 只交付本地 commit；体验整合 Agent 只整合、打包、部署和验活；两者都不推送 GitHub、不创建正式 tag。

正式公开有四条固定边界：

1. 正式发布只能基于已经完成体验验收的候选基线；
2. 候选之后发现的新提交不得未经体验直接加入正式版本；
3. 正式发布 Agent 按候选 SHA 复核文件树、更新正式版本说明并重新完成完整门禁；
4. GitHub 的 fetch、公开 commit、push、tag 和远端验真全部在专用发布服务器完成。

维护者 Mac 不得直接向 GitHub 执行 `git push`、`gh repo sync`、GitHub API 上传或其他 Git 写操作，也不得在服务器失败后改为本机直推。完整角色与交接规则见[多 Agent 协作规范](../开发协作/多Agent协作规范.md)。

## 1. 正式发布 Agent 接管前检查

普通开发 Agent 到这里已经停止：它们只交付分支、commit SHA、改动范围和验证结果。

正式发布 Agent 必须检查：

```bash
git status --short
git diff --check
git worktree list --porcelain
git branch --all --verbose --no-abbrev
git log --oneline --decorate -30
```

先读取体验候选记录，核对候选 Git SHA、预发布版本、tarball SHA-256、纳入提交、部署时间和观察结论。正式文件树必须与最后一次体验通过的候选一致；允许的差异仅限正式版本号、中英文版本说明、锁文件和由此产生的构建元数据。

建立正式发布提交表，确认每个纳入版本的功能都有明确 SHA、来源分支、用户可见变化、测试结果和体验证据。不得直接发布共享工作树中的未提交文件，也不得用“某个目录看起来最新”代替 commit 边界。

如果盘点发现候选之后还有希望纳入的新提交，默认放入下一轮体验候选。若用户要求本次纳入，必须停止正式发布，重新执行体验整合、部署和观察。正式基线、版本说明或关键配置发生变化后必须重新冻结。

## 2. 准备版本说明

只有正式发布 Agent 可以把体验候选的预发布版本收敛为正式 `0.x.x`，并更新锁文件、`docs/发布/版本记录/`、release commit 和 tag 候选。

中文版本记录必须使用 [中文版本说明模板](版本记录/中文版本说明模板.md)，并遵守：

- 用普通中文说明用户现在能做什么；
- 说明之前会遇到什么问题、现在如何改善；
- 说明是否需要重新登录、重启、修改配置或重新发送；
- 明确仍然存在的限制；
- 不写内部类名、字段名、文件路径、提交 SHA 和测试命令；
- 不使用“优化若干”“修复问题”“全面提升”等空泛说法。

技术细节、测试证据和 commit 清单放在发布验收报告或 commit body 中。

## 3. 发布前验证

至少运行：

```bash
git diff --check
npm run privacy:check
npm run lint
npm run typecheck:src
bun test test
npm run build
npm pack --dry-run --json
```

根据改动范围追加：

```bash
npm audit --omit=dev
npm run smoke:global -- --purge-global --clean-cache
```

WeRelay 不发布到 npm Registry。`package.json` 必须保持 `private: true`，发布流程不得执行 `npm publish`。

确认：

- lint、类型检查、测试和构建通过；
- tarball 包名、版本和发布说明一致；
- 包内不含 `.env`、私钥、日志、运行状态、附件、测试源码、`node_modules` 或本机路径；
- 所有公开位图都经过重新审查；
- 任何失败都保留为失败，不能用局部检查替代完整验收。

## 4. 导出无历史公开快照

在源仓库外选择一个不存在或为空的目录：

```bash
npm run public:snapshot -- ../WeRelay-public
cd ../WeRelay-public
npm install
npm run quality
npm pack --dry-run --json
```

快照脚本不会复制 `.git`、本地环境文件、密钥、`~/.werelay`、日志、附件、缓存、`dist` 或 `node_modules`。从 macOS 打包给 Linux 时必须设置 `COPYFILE_DISABLE=1` 并使用 `tar --no-xattrs`，再检查归档不存在 `._*` 文件。

本机快照目录不要执行 `git init` 或添加 GitHub remote。它只是经过审核的公开文件集合，不是发布仓库。

安全检查需要区分三个范围：

- `npm run privacy:check` 检查本次即将公开的当前文件树；
- GitHub 的 `Secret scan` 使用 Gitleaks 检查完整 Git 历史中的真实密钥模式；
- `npm run privacy:check:history` 用于补充审计旧图片、旧正式域名和已删除文件，它可能因为已知旧对象而失败，不能据此把“没有密钥泄露”写成“历史已经清空”。

如果补充历史审计仍有发现，发布报告必须逐项说明。彻底移除旧对象需要重写 Git 历史、冻结协作并改变公开提交 SHA；普通发布 helper 会拒绝这种 non-fast-forward 操作。没有用户对一次性历史重写的明确授权，不得强推或临时关闭保护规则。

## 5. 专用发布服务器

每个公开仓库使用独立目录和独立 GitHub deploy key，避免影响其他项目。例如：

```text
~/werelay-github-relay/
  incoming/       # 临时快照，0700
  repo.git/       # bare 仓库
  work/           # 每次发布的临时工作树
  push.log        # 发布审计，0600
```

私钥只保存在服务器，权限为 `0600`，不得复制回开发电脑或写入仓库、脚本参数、日志和聊天记录。

服务器 helper 必须：

- 先 fetch GitHub 当前 `main`；
- 以远端当前提交创建隔离临时工作树；
- 再次运行隐私检查；
- 创建公开 commit 后先推送到本次专用的候选分支；
- 等待完整历史密钥扫描与 Linux、macOS、Windows 质量检查全部通过；
- 再将同一个已验收提交 fast-forward 到 `main`，并删除候选分支；
- 等待期间如果远端 `main` 已变化，立即失败并重新开始；
- `main` 推送会再次触发同一组 CI；发布 Agent 还要等待这次最新运行结束，不能只引用候选分支的结果；
- 拒绝 non-fast-forward 和强推；
- 用 `git ls-remote` 验证最终 SHA；
- 清理本次临时文件；
- 不触碰服务器上的其他项目。

### 5.1 GitHub 仓库保护基线

公开仓库应保持以下设置：

- Secret scanning 已启用；
- Push protection 已启用；
- `main` 的状态检查使用严格模式，要求分支基于最新 `main`；
- 必须通过 `Secret scan`、`Quality (ubuntu-latest)`、`Quality (macos-latest)` 和 `Quality (windows-latest)`；
- 不强制 PR，以保留“服务器候选分支检查后 fast-forward”的发布方式；
- 不允许 force push，不允许删除 `main`；
- 管理员紧急入口不作为日常发布绕过方式，任何例外必须由用户明确授权并留下审计。

首次创建或修改保护规则时，GitHub 可能要求 Passkey、密码或验证器再次确认。Agent 必须停在确认页面等待用户完成，不能关闭检查、降低规则或换用其他写入方式绕过。

发布后可以在已登录环境执行只读验真；不得借此从维护者 Mac 发起 GitHub 写操作：

```bash
OWNER=your-account
REPO=WeRelay
gh api "repos/$OWNER/$REPO/branches/main/protection"
gh api "repos/$OWNER/$REPO/secret-scanning/alerts?state=open&per_page=100"
```

验真至少确认：四项检查名称准确、严格模式开启、force push 与删除关闭、未处理 Secret alerts 数量符合发布报告。

## 6. 标准发布命令

仓库提供 `scripts/publish-github-via-server.mjs`。机器地址、SSH 用户、私钥路径和远端 helper 路径必须通过参数或本机环境变量提供，不能硬编码进仓库。

```bash
node scripts/publish-github-via-server.mjs \
  --server user@publish.example.com \
  --identity ~/.ssh/werelay_publish_ed25519 \
  --remote-helper ~/bin/werelay-github-publish-remote \
  --message "chore: release X.Y.Z"
```

该命令在本机只做隐私检查、生成公开快照和上传归档；GitHub fetch、公开 commit、push 和验真在服务器执行。远端在 fetch 与 push 之间出现新提交时，本次发布必须失败并重新开始，不能强推。

可复用的服务器 helper 模板位于 `deploy/github-publish-server/werelay-github-publish-remote`。

## 7. GitHub 与本地安装包

GitHub 是 WeRelay 唯一的公开发布和版本来源，不创建 npm Registry 公共包。npm 只用于运行项目脚本、生成 tarball 和安装已审核的本地产物。

正式发布必须保留同一 tarball 的文件名和校验值，本机与公网服务器都安装该产物；更新检查读取 GitHub Release、tag 或 `main` 分支的版本信息，不访问 npm Registry。

## 8. 发布后验收

正式发布 Agent 必须核对：

- GitHub 远端 SHA 与服务器发布结果一致；
- 候选分支的四项检查和 `main` 推送触发的最新四项检查都已成功；
- 临时候选分支已删除，分支保护仍保持预期设置；
- GitHub 公开版本信息、远端提交和本地 tarball 版本一致；
- 本机安装版本和 `/app-version` 正确；
- 正式网页、API、Relay 和设备在线链路正常；
- 版本记录没有把未验证事项写成已完成；
- 服务器临时快照已清理，其他项目未受影响。

本机私有开发提交与服务器创建的公开 commit SHA 可以不同；以公开文件树、服务器审计结果和 GitHub 远端 SHA 作为正式发布证据。

## 9. 仅仓库维护时的处理范围

只修改仓库安全、CI 或发布文档时，先创建本地 commit，不自动改产品版本号、不部署 Relay，也不推 GitHub。只有用户之后明确要求公开这些仓库维护内容时，才按本文执行 GitHub 正式发布；只有运行文件发生变化时，才需要更新运行服务。
