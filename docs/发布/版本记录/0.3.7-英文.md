# WeRelay 0.3.7

## What changed

- During long-running tasks, the mobile web app keeps adding the current steps, commands, and plan instead of showing only a running timer. Accelerated history is now joined with the real task’s latest progress.
- After a task finishes, stale running state is cleared promptly so model, reasoning, and permission controls follow the real task state instead of staying locked by an old running badge.
- The permission control remains visible while loading or when its current state is temporarily unavailable, with a clear loading or unavailable label instead of disappearing from the composer.

- The mobile web app can now show and change the current task permission scope. Codex, DeepSeek Harness, and WorkBuddy keep the permission settings of the real task; changes are disabled while a task is running, and unrestricted access requires an extra confirmation to prevent accidental elevation.
- ClawBot task lists now render URLs, email addresses, file names, and local paths as plain text, while long task and project names are shortened. Lists stay readable and WeChat no longer turns these entries into misleading links.
- The mobile task board now shows saved content immediately and refreshes quietly in the background. If the board has no dedicated cache yet, it can first rebuild a useful view from each terminal’s recent task snapshot instead of showing an empty or skeleton-only screen.
- Opening a computer-local page or a file from the active project on mobile now shows real deployment progress, captures the latest content on every click, and automatically opens a temporary public preview. The preview only reads files from the active project or same-origin static resources from a loopback page, expires after 15 minutes by default, and does not expose the computer port directly to the internet.
- A local page that depends on live APIs, persistent connections, or another computer-side backend may only show its static portion in the temporary preview. Open the original link again whenever a fresh snapshot is needed.
- When the public page is waiting on a slow task read, creating tasks, sending messages, and other changes now reach the computer first instead of sitting behind old reads until they time out.
- If new-task creation meets a temporary network error or gateway timeout, the page retries once with the same stable creation identity. A first request that already succeeded still resolves to the same task instead of adding duplicate empty tasks.
- After a new task finishes its first turn, ownership is handed back to Codex Desktop more reliably. A temporary ownership conflict is retried, and a finished task is not reclaimed unnecessarily, reducing “already open in another application” errors.
- When the selected model is temporarily at capacity, the page now says that the model is busy and suggests retrying later or switching models instead of only reporting that no reply was generated.
- When the mobile web restores a previously failed new-task draft, pressing New Task now retries immediately with the same project and draft identity instead of only reopening the old failure screen.
- A failed creation now shows a short, safely escaped real reason below the message and on the empty-task screen, while keeping a clear retry action so users can tell whether the terminal is disconnected, busy, or affected by another problem.
- A new-task draft that has not failed and simply has no sent content still reopens normally without creating a duplicate.
- A newly created Codex task on the mobile web can now receive its first text and image together. The page waits until that first message has actually entered the new task before handing it to the desktop, so a task that was created successfully is no longer reported as failed.
- If the public request is slow, times out, or is retried, WeRelay reuses the same new task instead of creating several empty tasks. A new attempt is allowed only after creation has genuinely failed.
- The first message starts in the same real Codex task, and that task remains available to continue from Codex Desktop after the initial turn completes.
- ClawBot now remembers the most recently shown or notified task. A plain follow-up continues in that exact task even after switching terminals or restarting WeRelay instead of silently reaching another session.
- Task messages now include stable numbers: reply with a number to enter that task, or send “Task 6: continue” to deliver content to the exact task. Approval and input prompts still take priority, so a bare number is never forwarded to the model by mistake.
- `/h` and `/help` now show concise ClawBot instructions at any time, including before a terminal has been selected.
- The public page now refreshes relay snapshots only when the browser actually requests them. An idle or closed page no longer leaves autonomous task-list scans running, and full task messages are never relay-warmed in the background.
- Task boards and recent-task lists read the Codex catalog directly from the local read-only state database, without starting Codex or scanning a large set of old tasks.
- A temporarily unresponsive agent can no longer hold the whole task board open for the full Harness request timeout; other available tasks can return first.
- Targeted ClawBot messages connect to the real Codex desktop owner first, so a slow read-only metadata helper no longer blocks delivery to an existing task.
- An explicit WorkBuddy switch detects a stale desktop hook, restarts the app, waits until its desktop task handlers are actually ready, and then resumes the original task instead of failing on startup timing.
- WorkBuddy questions now appear as clear requests for additional information instead of tool approvals. Answers return to the original desktop task, and long waits for user input no longer hit the two-minute desktop RPC timeout.
- Codex, WorkBuddy, and CodeBuddy task lists now prefer desktop user-renamed or generated titles instead of falling back to the first message or task ID; the native title sources for the other supported agents were audited as well.
- Ordinary CLI tasks no longer expose their working-directory folder as a project name or split into artificial project groups. A project label is kept only when CodeBuddy, Reasonix, or a compatible ACP provider exposes a reliable explicit user rename.
- If WorkBuddy's previously selected task was deleted or rejected by the desktop runtime, WeRelay clears the stale selection and immediately keeps the terminal connected instead of probing several recent tasks and waiting through repeated timeouts. Task lists and history remain available, and the exact task is attached only when the user opens or sends to it.
- ClawBot now immediately acknowledges “Tasks” and terminal-switch requests with a loading message before sending the complete list, and the aggregate list header is shortened to “All tasks.”
- After a message is sent from ClawBot to any supported agent, WeRelay immediately explains whether it was accepted, queued, skipped as a duplicate, or not sent because the task is busy, and includes the matching task link.
- Aggregate and single-agent task lists now use the same clear “Running 🟢” marker.
- Standalone Grok CLI tasks now read Grok’s own session events: an executing turn shows “Running 🟢” and returns to idle after completion instead of always appearing inactive when it is not attached to a WeRelay companion.
- The web page can now show and switch reasoning effort for Codex and DeepSeek Harness tasks. Switching is temporarily disabled while a task is running and becomes available again after completion or stop.
- When neither the user nor the session has selected a reasoning effort, the web page now shows “Follow session” instead of guessing a default. Switching models preserves the session effort only when the new model still supports it.
- Each time the terminal menu opens, it refreshes real task state across all running terminals. Busy terminals show a breathing green dot and return to idle after completion instead of being missed when only the current terminal was refreshed.
- The former DSH abbreviation is now shown as the full “DeepSeek Harness” name throughout the mobile web page.
- DeepSeek Harness tasks recover project grouping from their real working directories across macOS, Linux, and Windows paths, restoring project pages and project-scoped task creation.
- Follow-up messages sent from the web while Codex is replying now stay in the original task queue and continue after the current reply. Long completion notices are also delivered in safe segments instead of stopping after the opening section.
- Web transcripts no longer show the internal `[tool_use]` and `[tool_result]` placeholders that Codex Desktop hides. Cached, accelerated, and paginated histories use the same exact-placeholder filter without removing normal explanatory text.
- Long-pressing a task on mobile now keeps the rename/copy-ID menu open instead of dismissing it through a release click or stray text selection, and the menu actions have larger touch targets.
- Using Select All inside one mobile message now limits the selection to that message body instead of including the sidebar, page title, or other messages.
- The web page stops its pending animation as soon as the latest AI reply or a trusted server state proves that the task has finished.
- Long-history image lookup and persisted runtime checks now have explicit bounds while recent input images remain available.
- The DeepSeek Harness model menu is grouped by provider, and the composer's model, reasoning, and permission chips are slimmer; longer model names wrap fully instead of being cut off with an ellipsis.
- When the currently selected DeepSeek Harness model has been retired or is unavailable, the task can still switch to any other available model; it no longer gets stuck unable to either send messages or change models.
- Codex tasks created from the mobile web now stay in the project they were created for instead of landing in the wrong project.
- Non-Codex terminals such as Claude Code and DeepSeek Harness now show the real task name in message headers instead of an internal session identifier.

## What you need to do

- No reconfiguration is required; restart WeRelay after installing the 0.3.7 release.
- Upgrading from 0.3.6 or earlier keeps your existing configuration and data; no re-login is needed.
- If WeChat completion delivery asks for a fresh message, send ClawBot one normal message to refresh the WeChat context.
