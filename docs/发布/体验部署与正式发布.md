# 体验部署与正式发布

WeRelay 采用“两阶段发布”：开发完成后先部署体验候选，经过一段真实使用后，再由用户明确决定是否发布 GitHub 新版本。

```text
开发 Agent 本地提交
→ 完成任务的 Agent 主动执行体验部署交接
→ 唯一体验整合 Agent 按提交号整合
→ 完整检查、打包并部署本机和公网 Relay
→ 真实使用与观察
→ 用户明确要求发布 GitHub 新版本
→ 正式发布 Agent 复核同一候选并通过发布服务器推送 GitHub
```

**体验部署不是 GitHub 正式发布。** 体验服务器可以在观察期内暂时领先 GitHub，但必须能够准确追溯到一个已提交、已验证、可回滚的候选基线。

## 1. 为什么分成两个阶段

直接把刚完成的代码同时推到 GitHub 和正式服务器，会把“可运行”与“已经过真实使用”混为一谈。两阶段流程把这两个判断分开：

- 本地提交保证每项开发工作有清晰边界，不会只留在某个 Agent 的临时目录；
- 体验部署让网页、ClawBot、桌面原任务和公网 Relay 在真实环境中接受验证；
- GitHub 正式发布只公开已经体验通过的文件树，避免刚合入的新改动未经观察就成为公开版本；
- 体验失败可以回滚运行服务，但保留 Git 提交和排查证据，不用删除或改写开发历史。

观察期不设固定天数，由用户根据改动风险和实际使用情况决定。运行代码完成提交后默认进入体验部署，不需要用户逐次下达部署指令；但这是每个 Agent 必须实际执行的收尾步骤，不是 Git commit 自动触发的后台服务。没有完成整合、安装和验活时，必须明确报告“已提交但尚未部署”，不能把“进入队列”写成已经运行新版本。用户没有明确要求发布 GitHub 新版本时，任何 Agent 都不得把体验候选推到 GitHub、创建正式 tag 或宣称已经发布新版本。

## 2. 第一阶段：开发提交与体验候选

### 2.1 开发 Agent 交付

普通开发 Agent 必须在独立分支和 worktree 中完成修改、测试和本地 commit，并交付：

```text
提交号
用户可见变化
主要修改文件
实际通过的测试
依赖提交
未解决风险
体验验收清单
```

没有 commit SHA 的内容不自动进入候选。归属不明的共享工作树修改必须先调查、验收并补成独立提交，不能直接把整个工作树打包部署。

### 2.2 体验整合 Agent 接管

体验部署是运行代码提交后的默认后续动作，不再要求用户逐次授权。开发 Agent 创建 commit 后必须继续完成部署交接：如果当前没有其他体验整合负责人，可以在完成全仓盘点后接管本轮候选；如果已有负责人正在整合或部署，则只交付 SHA 和验收项，由现有负责人纳入下一候选，不能并发覆盖服务器。

当前仓库没有“提交后无人值守自动部署”的后台协调器，因此负责当前任务的 Agent 不能在 commit 后直接结束。它必须亲自确认候选已经由唯一负责人接管并完成部署；若因并发锁、凭据、服务器或验收失败而无法完成，最终报告必须醒目标出尚未部署和具体阻塞原因。

同一时间只能有一个体验整合 Agent。它必须：

1. 盘点全部 worktree、分支、dirty state 和候选提交；
2. 在独立 release worktree 中按明确 SHA 整合，不能直接发布共享工作树；
3. 记录纳入、排除、重复和暂缓的改动；
4. 运行完整质量门禁；
5. 生成唯一 tarball，并用同一产物完成本机安装和公网 Relay 部署；
6. 验证服务健康、网页、API、设备在线、任务读取、消息发送与本次重点功能；
7. 保存候选清单和可回滚的上一个稳定产物；
8. 不执行任何 GitHub 写操作。

体验整合 Agent 可以创建整合 commit、修复集成冲突并维护候选元数据，但不能把候选称为 GitHub 正式版本。普通开发 Agent 不得跳过全仓盘点，拿自己的分支直接覆盖本机或公网服务。

### 2.3 候选版本标识

体验候选使用预发布版本，避免与已公开正式版混淆。例如，从正式版 `0.3.4` 准备下一版候选时可以使用：

```text
0.3.5-preview.20260826.1
```

同一天重新打包时递增末尾序号。体验期间每次改变源码、版本文件、配置模板或打包内容，都必须创建新 commit、重新运行检查、重新生成 tarball，并产生新的候选标识和观察基线。

每个候选至少记录：

```text
候选 Git SHA
候选版本
纳入提交
排除或暂缓项
产物文件名
产物 SHA-256
生成时间
本机安装位置和版本
服务器部署路径和版本
部署时间
验活结果
上一个可回滚产物
```

不得使用“服务器当前目录看起来最新”作为候选身份。运行中的文件树必须能由候选 Git SHA 和 tarball 校验值复现。

## 3. 观察期

观察期从最后一个候选成功部署并通过基础验活后开始。重点观察真实链路，而不只看自动测试：

- ClawBot 是否能连接、切换任务、发送消息并收到最终回复；
- 网页是否能认证、读取原任务、发送消息、处理审批和展示附件；
- 公网 Relay、短链、API、设备在线与断线恢复是否稳定；
- 桌面端是否继续使用原任务，是否出现重复发送、替代任务或界面意外唤醒；
- 日志、CPU、内存和重启次数是否符合预期；
- 本次改动的专项验收是否持续正常。

发现问题时：

1. 必要时先回滚到上一个稳定 tarball，恢复服务；
2. 在独立开发分支修复并创建新 commit；
3. 由体验整合 Agent 重新整合、验证和部署；
4. 用新候选重新开始观察。

回滚运行服务不等于回滚 Git 历史。禁止用 `reset --hard`、删除提交或覆盖其他 Agent 工作来掩盖失败候选。

## 4. 第二阶段：GitHub 正式发布

只有用户明确要求“发布 GitHub 新版本”“把已体验版本正式发布”等等价动作后，才能进入本阶段。正式发布只能基于已经完成体验验收的候选基线。

正式发布 Agent 必须先核对：

- 用户确认的候选 Git SHA、候选版本和 tarball 校验值；
- 观察期间的问题已经关闭或明确记录为已知限制；
- 当前候选文件树与最后一次体验部署一致；
- 候选之后出现的其他 Agent 提交没有被静默夹带。

**新提交不得未经体验直接加入正式版本。** 最终盘点发现的新功能或修复默认进入下一轮候选；如果用户要求本次纳入，就必须重新整合、部署并观察后再发布。

正式发布时：

1. 将候选预发布版本收敛为正式 `0.x.x` 版本；
2. 使用清晰、非技术化的中文版本说明记录已经体验过的用户变化；
3. 重新运行完整质量门禁并生成正式 tarball；
4. 验证正式 tarball 的内容与体验通过的候选文件树一致，允许的差异仅限正式版本号、版本说明和由此产生的锁文件或构建元数据；
5. 生成经过隐私检查、不含 `.git` 的公开快照；
6. 通过专用发布服务器隔离目录完成 GitHub fetch、公开 commit、候选分支 CI、fast-forward `main`、tag 和远端验真；
7. 用同一正式 tarball 更新本机和公网 Relay，并再次验活，确保 GitHub、安装产物和服务器运行版本一致。

维护者 Mac 禁止直接向 GitHub push，发布服务器失败时也没有本机直推回退路径。详细 GitHub 操作见[对外发布操作手册](对外发布操作手册.md)。

## 5. 完整质量门禁

体验候选和 GitHub 正式发布都至少运行：

```bash
git diff --check
npm run privacy:check
npm run lint
npm run typecheck:src
bun test test
npm run build
npm pack --dry-run --json
```

涉及 CLI、daemon、移动网页或公网 Relay 时，还要用实际 `npm pack` 产物完成安装、服务重启、真实任务和公网验活。任何失败都必须保留为失败，不得用局部测试或旧候选结果替代。

## 6. 默认动作与用户指令

为避免用户每次重复通知部署，按以下语义执行：

| 用户指令 | 默认动作 |
| --- | --- |
| 完成运行代码修改并创建 commit | 自动创建或更新体验候选，部署本机和公网 Relay；不推 GitHub |
| 完成纯文档、测试说明或 CI 维护提交 | 创建 commit 并进入下一候选清单；运行产物没有变化时不重启服务 |
| “只提交，暂不部署” | 仅在用户明确说出时暂停自动体验部署 |
| “继续观察”“先体验一段时间” | 保持当前候选，不修改 GitHub 正式版本 |
| “发布 GitHub 新版本” | 只基于已体验通过的候选执行正式发布 |
| “发布并部署”但未说明 GitHub | 仍只做体验候选部署；必须在报告中明确 GitHub 未发布 |

如果用户同时明确要求“推送 GitHub 并部署”，则可连续执行第二阶段，但仍必须先确认目标文件树已经完成体验验收；没有体验基线时，先完成第一阶段并报告，不得把刚整合的未知改动直接公开。
