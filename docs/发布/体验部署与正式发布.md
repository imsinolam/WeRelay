# 统一版本、部署与 GitHub 发布

> 2026-10-30 起采用统一版本规则。为兼容既有文档链接，保留本文件的历史文件名；旧的 preview / 正式版双版本规则已经停止。

## 1. 唯一版本规则

**所有新版本统一使用 `0.x.x`，只递增最后一位，不再使用 preview、rc、日期或正式版后缀。** 例如 `0.3.22 → 0.3.23 → 0.3.24`；末位可以超过 9，不因到 9 自动进位。未来如需调整前两位，由用户明确决定。

- 每个版本只能对应一个已提交源码和一份 tarball；版本已打包、部署或上传后不得覆盖为不同内容。
- 任何已锁定产物的源码、打包内容或版本元数据变化，都使用下一个未占用的版本，重新验证和打包；失败版本不复用。
- 选下一版本前同时检查本地版本记录、产物清单、两端安装和 GitHub Release/tag，取全部已占用版本中的下一号，避免只看 GitHub 而覆盖未公开的部署版。
- 部署与 GitHub 公开是同一版本的两个状态，不是两套版本号；仅把同一包公开到 GitHub 时不再次改号、不重新打包。
- 历史 preview、rc 和 2.x 说明保留用于追溯，不改写旧版本，也不再沿用旧编号方式。

## 2. 开发、部署、公开仍分别授权

版本统一不等于开发提交自动上线。协作只分开发 Agent 与发布 Agent：开发 Agent 实现、验证、精确提交并登记；发布 Agent 在用户明确要求后集中整合、打包、部署或公开。单次部署和 GitHub 发布由同一负责人串行执行，不增设独立中间集成角色。

```text
开发 Agent 实现、验证并提交
→ 登记完整 SHA、依赖、验证与风险，等待用户明确指令
→ 发布 Agent 盘点并整合全部已完成提交
→ 完整门禁、锁定统一版本、生成唯一 tarball
→ 按用户要求安装本机 / 公网，或通过服务器公开 GitHub
→ 报告各位置实际版本、校验值、检查结果与待用户体验项
```

- “部署最新版”：只安装和部署，不自动推 GitHub、建 tag 或发布 Release。
- “发布 GitHub 新版本”：公开指定的、已通过完整门禁的文件树；若已部署的是同一版本同一产物，直接复用，不为“转正式”再改号。
- “发布并部署”或同时明确要求 GitHub 与两端更新：由发布 Agent 连续完成公开和同包安装，不另设 preview 阶段，也不要求先等固定天数再公开。
- “发布，不要部署”：只公开 GitHub，不安装、不重启任何服务，检查当前运行版未被改变。
- 完成代码提交不自动部署，必须等待用户明确的集中部署指令；不能并发覆盖服务器，未实际完成时报告“已提交但尚未部署”。
- 未提交或归属不明的代码先按[多 Agent 协作规范](../开发协作/多Agent协作规范.md)分类，不能直接打包共享脏工作树。

## 3. 发布 Agent 的固定步骤

1. 核对全部 worktree、分支、脏文件、本机与开发服务器提交、GitHub 当前文件树和已安装版本，记录纳入、等价重复、暂缓及原因。
2. 从现行 WeRelay 源码新建独立发布工作树，按明确 SHA 整合；保留其他任务的未提交修改，不从旧 DeskRelay 历史整棵覆盖。
3. 确定下一未占用的统一版本，更新包与锁文件、中英文版本说明，说明用户可见变化及已知限制。历史文档不伪造为新规则。
4. 运行完整门禁；只从干净提交构建唯一 tarball，检查文件清单与隐私，记录源码 SHA、tarball SHA-256。
5. 需要 GitHub 公开时，先导出无 `.git` 的审查快照，通过专用发布服务器隔离目录完成 fetch、公开 commit、一次性候选分支 CI、fast-forward main、tag、Release 与远端验真。这里的候选分支只是 CI 临时分支，不是另一个产品版本。
6. 需要部署时，用同一 tarball 串行安装本机和公网 Relay，保留旧包与回滚目录；只重启项目专属服务，不改其他项目。
7. 检查服务、安装文件、网页及资源版本、只读 API、短链、deviceOnline 与中继连接。若实际检查失败，明确失败并恢复可用状态，不能拿测试通过代替部署成功。
8. 留存完整记录并安全回收本轮临时资源。GitHub 失败不回退 Mac 直推，不强推，不降低分支保护。

## 4. 完整质量门禁

每个新版本至少运行：

```bash
git diff --check
npm run privacy:check
npm run lint
npm run typecheck:src
bun test test
npm run build
npm pack --dry-run --json
```

用实际 tarball 做隔离安装冒烟，再安装目标环境；不从 Registry 下载替代 WeRelay 包。依赖按源码锁定，不在部署时顺手升级。纯文档任务先精确提交并登记，不单独触发部署；当用户要求把它公开为一个新版本时，仍执行版本门禁。

同一已锁定产物的源码和相关输入未变化时，可以复用对应验证证据，但必须注明来源、时间和覆盖范围；内容变化必须重新验证，不得复用旧文件树的通过结论。

## 5. 部署后的验活分工

**真实 Agent 与 ClawBot 的收发、审批和最终回复回推由用户部署后自行验收。** 发布 Agent 不自动发送测试消息、不操作真实审批，不为验活打开、切换、恢复或重启 Agent 应用/任务，不创建替代任务；历史专用验活任务不构成持续授权。用户另外明确要求专项验活时再执行。

发布 Agent 必须完成基础检查，报告分别说明“部署结果”“基础检查结果”“用户体验验收：待用户确认”。待用户体验不冒称通过或失败，也不单独阻止用户已经明确授权的 GitHub 发布；基础异常、安全问题与已知风险必须报告，不能隐瞒。

`refs/werelay/active-baseline` 是已验收开发基线，不等于最新安装或最新 GitHub 版本。仅在用户确认真实体验且两端基础检查通过后推进；公开 Release 本身不自动证明真实体验通过。未确认前保留最新源码分支和 manifest 供下一任务准确选基线。

## 6. 回滚、记录与公开边界

每次记录时间（含时区）、Agent、实际模型（未知写 unknown）、任务名/id、分支、完整源码 SHA、版本、tarball SHA-256 与路径、纳入/排除清单、各端安装路径与状态、验证和风险、可回滚版本，以及 GitHub 是否公开。不得把私钥、令牌、用户数据或真实配置写入 Git/公开包。

回滚只切换运行产物，不删除或重写 Git 历史；保留失败版本号和证据。修复后使用下一版本，不能覆盖已分配版本。

GitHub 是唯一公开分发来源，`package.json` 保持 `private: true`，不发布 npm Registry。Mac 仅负责验证、打包、生成隐私审查快照和上传；GitHub 写入与远端验真遵循[对外发布操作手册](对外发布操作手册.md)。
