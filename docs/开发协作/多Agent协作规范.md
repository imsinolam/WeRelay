# WeRelay 多 Agent 协作规范

> 本文是 WeRelay 多 Agent 开发和发布的强制规范。任何 Agent 在修改仓库前都应阅读本文；`AGENTS.md` 负责给出仓库级硬约束，本文负责解释完整协作流程。

WeRelay 允许多个 Agent 同时工作，但开发与发布必须按清晰边界完成；需求合流由开发负责人完成，版本锁定、部署和 GitHub 公开由同一发布角色负责，不增加中间角色。目标不是“尽快把当前目录提交掉”，而是保证每一项改动都可追踪、可验证、可回滚，不覆盖其他 Agent，也不遗漏已经完成的任务。

> **验活职责更新（2026-10-28）**：部署 Agent 保留完整门禁、同包安装及基础检查；真实 Agent 原任务收发、审批和 ClawBot 收发／回推验活改由用户部署后自行完成，不自动发送验活消息或操作任务。报告分别说明部署结果与待用户确认的体验，不以未代做体验作为部署阻塞；实际基础异常仍须报告。本文旧的“真实任务验活”描述按此分工解释，详见[体验部署与正式发布](../发布/体验部署与正式发布.md)。已验收基线及正式发布仍须用户验收反馈，不自动推进。

> **统一版本规则（2026-11-05）**：所有新版本只用 `1.x.x`，末位逐次递增，不再生成 preview/rc 或“转正式”版本。同一版本只对应一个源码与 tarball；部署和 GitHub 公开是两个授权状态，可以复用同一产物。本文历史角色名“体验整合 Agent / 正式发布 Agent”均指发布 Agent 在不同授权动作中的职责，不是额外角色。以[统一版本、部署与 GitHub 发布](../发布/体验部署与正式发布.md)为事实真源。

> **需求交付规则更新（2026-11-14）**：每一个需求都必须先自测通过、精确提交并合入最新本地 `main`，才算开发交付完成。该规则替代过去“开发只提交、发版再汇总分支”的分工，适用于功能、修复和规范文档；不授权自动部署或 GitHub 写入。

## 1. 三条最高原则

1. **开发完成必须自测、提交并合主线。** 完成状态不能只存在于聊天记录、共享工作树或任务分支；缺少必要自测、提交或本地 `main` 合入证据，均属于未完成交付。
2. **发布只从 main 锁定，不临时拼分支。** 未合入需求和未知脏改动保留并登记给原负责人，不随版、不阻塞发布；不能夹带，也不能把它们冒称已发布。
3. **正式版本只有一个发布负责人。** 开发 Agent 负责本需求合入本地 `main`，不改版本号、不推 GitHub、不部署；发布 Agent 只在用户明确授权后接管一次版本。

## 2. 角色与责任

### 2.1 开发 Agent

开发 Agent 负责一个边界清晰的功能或修复。

**每次修改前都必须先把仓库检查到最新状态**，再动任何文件。这不是一次性动作：只要中途切换到新任务、新分支或新 worktree，就要重新检查一遍。开始前必须：

```bash
git status --short --branch
git worktree list --porcelain
git branch --all --verbose --no-abbrev
git log --oneline -5
git log --oneline --all --since="7 days ago"
```

检查内容：

- 当前分支、HEAD SHA 和 dirty state，确认没有他人未提交改动被自己覆盖；
- 最新本地 `main` 完整 SHA 是否已经前进，自己的起点是否过期；不能把文档里记录的某个版本号、旧 worktree 的分支名或本机根目录当成永远最新的基线；
- 所有 worktree 和分支里是否存在与本任务重叠的更新或已完成提交；
- 是否存在同名的旧分支或 worktree 残留。

本仓库不配置 GitHub remote，GitHub 写操作只在专用发布服务器执行。因此开发前先在目标 worktree 根目录执行 `npm run baseline:check -- --active`：它读取所有 worktree 共享的 `refs/werelay/active-baseline`，拒绝旧产品身份、2.x 版本和非活动运行基线后代。由体验整合负责人维护该引用，开发 Agent 不得自己更改。旧工作树如果连检查命令都没有，**不是豁免**：停止在旧分支写代码，到现行工作树查明活动基线，确认最新本地 `main` 包含该运行基线后，从最新 `main` 创建新的 worktree 移植旧提交的功能意图；旧提交不能直接接续开发。本机安装的共享 Git `pre-commit` 守卫会在所有 worktree 执行同样检查，但它只是最后防线，不能代替修改前检查，也不得用 `--no-verify` 绕过。正式发布仍须按 `docs/发布/对外发布操作手册.md` 在专用发布服务器查询 GitHub `main` 与 tag；本地基线检查不能代替远端新鲜度验真。

体验整合负责人在已部署候选的**现行 WeRelay 工作树**执行 `npm run baseline:install-hook -- --base <成功部署并验活的完整 SHA>`。首次执行会安装本机仓库所有 worktree 共用的提交守卫并记录基线；后续在用户确认真实体验且两端基础检查通过后重跑，引用只能沿现行历史前进。脚本遇到已有自定义 hooksPath、未知 pre-commit 或断代候选会拒绝覆盖，须人工整合，不能强行绕开。这个本机 Git 引用不推送 GitHub，换电脑或重新 clone 后要由负责人重新建立。

开发起点使用最新本地 `main`，活动引用只是运行基线安全守卫，不要求先部署 main。发现 main 已前进时，先把自己的起点 rebase 或重新开 worktree 到最新 main，再开始修改；不要基于过期基线继续开发，否则后续整合必然产生冲突。开始修改前必须记录基线 SHA。

开发规则：

- 使用唯一分支和独立 worktree，不在共享 `main` 直接开发；
- 记录起始基线 SHA，只修改自己负责的文件；
- 不执行 `git reset --hard`、`git checkout -- <file>`、清空他人 stash 或删除未知 worktree；
- 不使用 `git add -A`、`git add .` 等可能夹带他人改动的命令，必须显式暂存本任务文件；
- 发现与其他 Agent 修改同一逻辑时，停止扩大范围并报告冲突；
- 完成后运行与风险匹配的测试并创建一个或多个本地 commit；
- 自测通过、精确提交后，按下节安全合入最新本地 `main` 并核验；不推送远端，不创建 tag，不修改正式版本号，不发布 npm，不部署共享环境；
- 不从维护者 Mac 执行任何 GitHub 写操作。

完成交付必须包含：

```text
分支：<branch>
基线：<base SHA>
提交：<需求完整 commit SHA，可多个>
合入 main：<合入后的完整 SHA 与祖先关系核验结果>
状态：已合主线、尚未部署
改动：<用户可感知变化>
文件：<主要修改范围>
验证：<实际运行并通过的命令>
依赖：<前置提交或无>
遗留：<未验证、风险或无>
体验验收：<需要在本机或公网确认的行为>
```

如果任务还没有提交或尚未合入 `main`，必须明确写“未完成交付”及阻塞原因，不能只说“代码已经写好”或把“待整合”当作完成。

#### 每项需求的合主线步骤（开发负责人执行）

1. 在本需求独立 worktree 完成风险匹配的自测，显式暂存自己的文件并提交；提交前检查 `git status --short --ignored`，不带入其他任务、凭据或运行数据。
2. 重新读取最新本地 `main` SHA。在本需求分支组合最新 main（未共享的任务提交可 rebase，或 merge main），由需求负责人按功能意图解决冲突并检查组合差异；不能整文件覆盖较新的修复。合流后的文件树有变化时重跑受影响自测，共享逻辑扩大回归；未变化且输入一致的证据可追溯复用。
3. 串行推进本地 `main`，只能快进且必须保留所有已有提交。不在他人的工作区操作，不使用强制更新、reset 或跳过 hook。必须使用共享 Git 目录下的 `werelay-main-land.lock` 作为所有开发和发布任务共用的短期合流锁：用 `mkdir` 排他获取，记录任务、进程、工作树与时间；占用时等待/协调，不能擅自删除未知或仍在使用的锁。锁只用于最终核验和推进，耗时测试在锁外进行；创建、切换或移除检出 main 的工作区也须使用同一锁，避免核验后 main 又被检出。操作结束只释放自己持有的锁，失败同样释放；Git 自身的 ref 锁与 compare-and-swap 校验仍须保留，不能只依赖约定锁。
4. `main` 没有被任何 worktree 检出时，可以在锁内按下面的 compare-and-swap 操作推进；若已被检出，必须由该工作区负责人确认无人使用且干净后，在该现场执行 `git merge --ff-only <已验证任务 SHA>`。不能用 update-ref 绕过已检出 main 的索引/工作区，不得另建强制检出副本。需要协调期间本需求仍未完成交付。
5. 推进后核验需求提交是当前 main 的祖先、main 没有丢失原有提交，记录需求 SHA、main SHA、自测及冲突情况。若竞争导致 main 前进，回到第 2 步组合新 main 并补验，不能盲重试旧树或强行覆盖。

在自己的干净任务 worktree 中，以下命令仅为第 3–5 步**持有共享合流锁、确认 main 未被检出后**的操作样例；`mainBefore` 必须是本次已经组合并测试的 main SHA，不能临推进才读取一个未测试的新值：

```bash
# mainBefore=<本次已组合并测试的完整 main SHA>
requirement=$(git rev-parse HEAD)
git merge-base --is-ancestor "$mainBefore" "$requirement" || exit 1
# 任一工作区检出 main 就停止此路径，交由该工作区负责人快进。
if git worktree list --porcelain | grep -qx 'branch refs/heads/main'; then exit 1; fi
git update-ref -m "land validated requirement" refs/heads/main "$requirement" "$mainBefore" || exit 1
git merge-base --is-ancestor "$requirement" main || exit 1
git merge-base --is-ancestor "$mainBefore" main || exit 1
git rev-parse main
```

该流程只授权本地 main 合流，不新增 GitHub push、建 tag、版本号修改或部署权限；活动运行基线引用不随合流推进。子 Agent 只向开发主控交付成果，由主控收口成一个需求后合流，不要求各子任务分别合 main。现有未合入任务由原负责人按此流程补齐，不能批量把未知历史分支塞入 main。

### 2.2 体验整合 Agent

体验整合 Agent 是发布 Agent 的历史称呼，现职责是从已合入的本地 `main` 锁定版本和部署，不再承担各需求分支的集中合并。仅在用户明确要求统一部署时开始；需求负责人完成自测、提交、合 main 和登记即可，不自动唤起发版任务。

“自测、提交、合入 main、核验并登记”是开发 Agent 的强制收尾职责；Git 提交不自动触发部署，单项开发不得自行唤起部署任务。当前任务 Agent 必须确认候选实际完成版本锁定、安装和基础验活后才能报告部署完成；如果因并发、凭据、服务器或验证失败而停下，必须明确报告“已合入 main，尚未部署”和阻塞原因。

体验整合 Agent 负责：

- 核对最新本地 `main` 与上次发布的差异和合流记录，锁定明确的 main SHA；
- 盘点未合入分支和未提交修改，保留并交原负责人继续，不随版、不阻塞发布；
- 从 main 创建独立 release worktree，不汇总需求分支或临时 cherry-pick；
- 完成必要版本元数据、安全合回本地 main 后冻结，并运行组合发布门禁；
- 使用可追溯的统一 `1.x.x` 版本打包唯一 tarball；
- 完成隐私、质量、构建、打包、本机安装和线上验活；
- 将同一产物部署到公网 Relay，记录 SHA-256 和回滚产物；
- 报告纳入、排除、重复和仍待处理的改动；
- 在每次候选内容变化后重新验证、部署并重置观察基线；
- 串行处理部署，防止多个 Agent 用不同候选互相覆盖。

体验整合 Agent 不得：

- 执行 GitHub 写操作、创建正式 tag 或宣称正式新版本已经发布；
- 把共享工作树整体当作候选输入；
- 把未提交或未合入的需求冒称已发布，或不说明其保留状态；
- 为了凑齐候选临时扩展业务功能，代开发补提交、处理单项需求冲突或绕过合主线要求；
- 覆盖其他 Agent 的未提交工作；
- 把未验证事项写成已经完成。

### 2.3 正式发布 Agent

正式发布 Agent 是某一 GitHub 版本唯一的公开发布负责人。只有用户明确要求“发布 GitHub 新版本”等等价动作后，才能承担这个角色。

正式发布 Agent 负责：

- 从本地 main 锁定本次用户明确授权公开且已通过完整门禁的源码基线，单独记录用户体验状态；
- 确认候选之后的新提交没有被静默夹带；
- 使用统一 `1.x.x` 版本和同一 tarball，更新中英文版本说明；不为公开再改号；
- 重新运行完整门禁并生成正式 tarball；
- 验证公开文件树、安装文件和唯一 tarball 一致，用户体验状态单独记录；
- 通过专用发布服务器完成 GitHub fetch、候选分支检查、fast-forward push、tag 和远端 SHA 验真；
- 用同一正式 tarball 更新本机和公网 Relay，并再次完成线上验活。

正式发布 Agent 不得：

- 把未经过明确纳入审查和完整门禁的新提交直接加入公开版本；
- 在候选已变化时继续沿用旧验收结论；
- 在发布服务器失败后改为从 Mac 直推 GitHub；
- 为通过 CI 临时关闭分支保护、强推或删除 `main`。

### 2.4 验收或产品 Agent

验收 Agent 可以复现问题、定义验收标准和检查线上体验，但不代替开发 Agent 交付提交，也不代替体验整合 Agent 或正式发布 Agent 执行其专属动作。详细职责见[任务职责与分工](任务职责与分工.md)。

## 3. 共享工作树规则

共享 `main` 不应成为并行开发目录。合流优先在各自任务分支组合、自测，再按 2.1 节串行安全快进 main；已检出 main 的现场只能由其负责人确认干净且无人使用后推进，不能让普通开发随意修改他人现场。

如果发现共享工作树有未提交修改：

1. 立即记录文件列表，不执行覆盖、回滚或清理；
2. 检查所有 worktree 和分支，寻找对应提交；
3. 比较文件内容或补丁，判断是否为已提交任务的重复副本；
4. 查找负责 Agent 的交付信息、测试和依赖；
5. 在归属不清前，不继续在这些文件上叠加修改。

禁止用以下方式“恢复干净”：

```text
git reset --hard
git checkout -- <file>
git restore <unknown-file>
git clean -fd
git stash 后删除或覆盖 stash
```

共享工作树脏状态本身是需要处理的协作事件，不能当作普通噪声。

## 4. 未提交改动的强制分类

开发负责人负责自己的未提交修改；发布 Agent 盘点发现的遗留按以下分类登记保留，不临时恢复后塞入发布范围。未知历史遗留不阻塞只从 main 发布。

### A. 已提交任务的重复副本

判断依据可以包括：

- 工作区文件与某个候选提交或 release 分支内容完全一致；
- 补丁与已提交功能等价；
- 对应分支有明确测试和交付记录。

处理方式：

- 发布时使用正式提交 SHA，不使用共享副本；
- 在报告中注明“已通过提交纳入，当前脏文件是重复副本”；
- 发布后再按安全清理流程处理共享副本。

### B. 已完成但遗漏提交

必须同时满足：

- 功能边界清楚；
- 可以识别负责人或修改来源；
- 测试和验收结果可复核；
- 与当前发布基线没有未解决冲突。

处理顺序：

1. 登记为“未完成交付”，保留原现场并交原开发负责人；
2. 原负责人补建提交、自测并合入 main，不能由发版任务临时补交付；
3. 原负责人不可用时，明确安排后续开发负责人在独立恢复分支保存、审查、验证并合入；
4. 未合入时不随版、不阻塞当前发布；合入后等待下一次发布冻结，不静默夹带进已锁定产物。

不得直接在共享 `main` 上执行 `git add . && git commit`。

### C. 未完成或无法确认

包括：

- 没有测试；
- 只有部分文件；
- 依赖关系不明；
- 同时包含调试内容；
- 无法确认用户可见行为；
- 与其他已发布修复冲突。

处理方式：保留并明确排除，不得发布，也不得描述为“已完成”。

### D. 会覆盖已验证修复的过期版本

例如共享目录中的文件基于旧基线，缺少后来加入的 Windows、审批、生命周期或安全修复。

处理方式：

- 不能整文件覆盖；
- 只允许从中提取仍有价值的独立 hunk；
- 提取后重新运行相关回归测试；
- 在新提交中说明保留了哪些较新的行为。

## 5. 锁定版本或正式发布前盘点

体验整合 Agent 或正式发布 Agent 开始前至少运行：

```bash
git status --short --branch
git diff --check
git worktree list --porcelain
git branch --all --verbose --no-abbrev
git log --all --oneline --decorate -40
```

从 main 锁定源码后，建立相对上一版本的差异与保留项表（不是待 cherry-pick 清单）：

| 提交或改动组 | 来源 | 用户变化 | 验证 | 与其他提交关系 | 处理结论 |
| --- | --- | --- | --- | --- | --- |
| SHA / dirty group | branch / worktree | 一句话 | 通过 / 风险 | 独立 / 重复 / 冲突 / 依赖 | 已合主线纳入 / 未合保留 / 排除 |

冻结候选或正式发布范围前必须回答：

- 所有干净 worktree 的新提交是否都已检查？
- 所有脏 worktree 是否都已分类？
- 是否存在“完成但未提交”的任务？
- 是否存在内容等价但 SHA 不同的 cherry-pick？
- 当前 release 基线是否来自 main、包含上次已部署的全部修复？
- 未合入任务是否保留给原负责人，未被临时合并或作为本次发布阻塞？

## 6. 统一版本的部署与公开流程

完整流程见[体验部署与正式发布](../发布/体验部署与正式发布.md)。体验部署与 GitHub 公开仍分别授权，但共享同一版本与产物，不再使用两套版本号。

### 6.1 冻结候选范围

- 确定当前公开正式版和下一候选版本；
- 锁定当时本地 main 的完整 SHA，确定相对上一版已合入的需求；
- 记录排除项和原因；
- HEAD、候选提交、打包内容或关键配置变化后重新冻结；
- 不把共享工作树的未提交内容直接纳入候选。

### 6.2 从 main 锁定发布树

- 从最新本地 main 创建独立 release worktree，不临时汇总任务分支；
- 发布专属版本号、锁文件和版本说明形成提交，也按 2.1 节安全合入本地 main 并核验；
- main 若前进，由发布负责人组合最新 main 并补充相关验证，再合流和重新冻结；不得覆盖他人提交；
- 冻结后 main 继续前进，不自动夹带新需求；本次只验证和发布已锁定源码，下一次再从更新后的 main 取数；
- 单需求冲突或回归交其开发负责人修复并合 main，再决定是否重新冻结，不重写其他 Agent 的分支历史。

### 6.3 第一阶段：体验候选部署

需求自测、提交并合入 main 后登记待发布；用户明确要求集中部署时，从当时 main 锁定范围再启动本阶段，不临时补收各任务分支。发布 Agent 使用统一版本，例如 `1.0.0`（下一版 `1.0.1`），并记录候选 Git SHA、纳入提交、tarball 文件名、SHA-256、部署位置、部署时间、验活结果和回滚产物。纯文档、测试说明或 CI 维护没有改变运行产物时，只记录到下一候选清单，不为此单独重启服务。

体验候选必须：

- 完成完整质量门禁；
- 使用实际 `npm pack` 产物，而不是直接复制源码覆盖服务；
- 用同一 tarball 完成本机安装和公网 Relay 部署；
- 验证本机服务、网页、只读 API、版本一致性、设备在线和中继连接；真实 Agent／ClawBot 消息与审批体验交由用户；
- 保留上一个稳定 tarball 和安全回滚步骤；
- 明确报告“GitHub 尚未发布”；
- 不创建正式 tag，不执行 GitHub 写操作。

**体验部署不是 GitHub 正式发布。** 服务器在观察期内可以暂时领先 GitHub，但运行版本必须可由候选 SHA 和 tarball 校验值复现。

### 6.4 观察与修复

观察期由用户决定，不设固定天数。发现问题时可以先回滚运行服务，但必须保留失败候选的 Git 提交和证据。修复应由开发负责人在独立分支完成自测、形成新 commit 并合入 main，再由发布 Agent 按授权重新锁定、验证、打包和部署。

只要已经锁定产物的源码、配置模板或打包内容变化，就必须递增统一版本末位，并从最新成功部署重新开始观察。旧候选的自动测试和体验结论不能直接覆盖新文件树。

### 6.5 第二阶段：GitHub 正式发布

只有用户明确要求发布 GitHub 新版本，正式发布 Agent 才能开始：

- 公开基线必须完成完整门禁并得到用户明确发布授权；真实使用验收按用户分工单独记录，不冒称已经通过；
- 新提交必须明确审查、纳入清单并通过完整门禁，不得静默夹带；
- 沿用同一 `1.x.x` 版本、源码和 tarball，公开动作不再次改号；内容变化则使用下一个未占用版本；
- 重新运行完整质量门禁并生成正式 tarball；
- 公开文件树、安装包与部署清单必须对应同一源码；同一版本不得覆盖为不同内容；
- Mac 只生成经过隐私检查、不含 `.git` 的公开快照；
- GitHub fetch、公开 commit、push、tag 和 `git ls-remote` 验真只能在专用发布服务器完成；
- 公开 commit 必须先进入一次性候选分支，等待 Secret scan 与 Linux、macOS、Windows 全部通过，再把同一 SHA fast-forward 到 `main`；
- `main` 必须保持四项检查的严格分支保护，禁止 force push 和删除；不得为了通过发布临时关闭保护；
- `main` 推送触发的最新一轮四项 CI 也要完成验真，不能只引用候选分支结果；
- 推送必须 fast-forward，拒绝强推和 non-fast-forward；
- 最终使用同一正式 tarball 更新本机和公网 Relay，再次验活并保留回滚目录；
- 详细 GitHub 操作见[对外发布操作手册](../发布/对外发布操作手册.md)。

### 6.6 完整质量门禁

体验候选和 GitHub 正式发布至少都运行：

```bash
git diff --check
npm run privacy:check
npm run lint
npm run typecheck:src
bun test test
npm run build
npm pack --dry-run --json
```

涉及 CLI、daemon、全局安装或正式网页时，还要执行实际 tarball 安装、服务重启、真实任务和公网验活。失败必须保留为失败，不能用局部测试或旧候选结果替代。

### 6.7 正式发布后验收

至少核对：

- GitHub 远端 SHA；
- 候选分支与 `main` 最新运行的 Secret scan 和三平台 CI，特别是 Windows；
- `main` 分支保护、候选分支清理和未处理 Secret alerts；
- 本机安装版本和健康状态；
- 公网网页、认证 API、Relay 设备在线；
- 任务读取、消息发送和回读；
- 本次涉及的审批、通知、附件或缓存行为；
- 未纳入改动仍被安全保留；
- 正式服务器安装的 tarball 与 GitHub 正式文件树一致。

## 7. 合流及发布后清理

开发负责人在合 main 并登记证据后，按归属入口回收本需求不再使用的临时 worktree 与专属可重建缓存，不必为等待发版保留整份 checkout。先确认提交已进入 main、有持久引用、无脏文件（含忽略/未跟踪必需资产）、无运行进程或共享引用；Codex 托管工作区走托管入口，项目登记工作区走项目入口，普通 Git worktree 才用 Git 移除。不能强删他人现场；存在阻塞时记录绝对路径、归属、保留原因与解除条件。

发布 Agent 负责本轮 release 工作区及已明确交接的清理遗留，不批量清理其他任务。发布成功不等于可以立即删除分支和 worktree。

清理顺序：

1. 记录已发布版本、公开 SHA 和本地 release SHA；
2. 将共享脏状态与已发布基线逐文件比较；
3. 对重复副本保存分类证据后再清理；
4. 把独有且有价值的改动迁移到新分支并提交；
5. 确认没有唯一内容后，才删除临时 worktree、过期分支和快照；
6. 不自动删除其他 Agent 仍可能使用的工作区。

发布报告必须区分：

- 已提交且已发布；
- 已合主线但未发布；
- 已提交但未合主线（未完成交付）；
- 已发布提交的重复脏副本；
- 未完成或无法确认的修改；
- 仍需下一版本处理的独有改动。

## 8. 版本说明写法

中文版本说明是面向用户的主记录，使用[中文版本说明模板](../发布/版本记录/中文版本说明模板.md)。

应该写：

- 用户现在能做什么；
- 之前遇到什么问题，现在如何改善；
- 是否需要重启、登录、重新发送或修改配置；
- 仍存在什么限制。

不应该写：

- 类名、字段名、内部路径和大段提交 SHA；
- “优化若干”“修复问题”等空话；
- 没有实测依据的“彻底解决”“全部支持”；
- 把未发布或未验收的功能写成已经上线。

技术细节和测试证据放在 commit body、候选表和发布验收报告中。

## 提交与部署可追溯记录

每次提交、体验部署和正式发布都必须使用[提交与部署记录模板](提交与部署记录模板.md)，记录真实时间、Agent、实际模型（未知写 unknown）、任务名与任务 ID、分支、完整源码 SHA、版本、产物 SHA、路径、验证和风险。不得猜测身份或将提交成功当成部署成功。

体验候选只能从已提交源码构建，使用同一 tarball 串行安装本机与公网；禁止未来日期和同版本覆盖。只有体验整合负责人可以将候选标记为已部署。发现未记录部署应先保留现场、核对身份，不能直接覆盖。部署前先核对正式域名实际解析目标、设备配置与服务路径；其他服务器健康不能证明正式公网已更新。

## 单一主线与临时工作区

隔离 worktree 是并行修改的临时工作面，不是长期产品分叉，也不是运行程序自动采用的源码。安装的是验收过的 tarball；工作区文件修改不会自动更新后台程序。

- 开发起点以最新本地 main 为准，并通过活动运行基线安全守卫，不能使用历史主目录中的旧分支。
- 每项需求自测、提交并由开发负责人合入 main 后，登记需求和 main 完整 SHA；发布负责人只从 main 锁定发布范围，运行实例只使用该主线构建的一个包。
- 需求合 main 并核验后，由开发负责人按上节回收本需求临时工作区；保留必要验收材料，不因尚未发布无限保留 checkout。
- 用户要求统一主工作区时，先盘点并归档该目录已有修改，再由整合负责人推进到验收主线；不得直接覆盖共享旧目录或删除未知工作区来“统一”。

交付必须区分“未完成交付（未自测/未提交/待合主线）”“开发完成且已合主线”“已安装”“真实验收通过”；不得让用户把另一工作区的修复误认为已在当前后台运行。部署清单应同时记录候选 SHA、安装包版本与校验值、运行入口以及活动基线引用；引用与安装版本不一致要明确记录和校正，不能由开发 Agent 随意推进基线来掩盖。
