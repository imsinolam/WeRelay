# WeRelay 多 Agent 协作规范

> 本文是 WeRelay 多 Agent 开发和发布的强制规范。任何 Agent 在修改仓库前都应阅读本文；`AGENTS.md` 负责给出仓库级硬约束，本文负责解释完整协作流程。

WeRelay 允许多个 Agent 同时工作，但代码开发、版本整合和正式发布必须由不同角色按清晰边界完成。目标不是“尽快把当前目录提交掉”，而是保证每一项改动都可追踪、可验证、可回滚，不覆盖其他 Agent，也不遗漏已经完成的任务。

## 1. 三条最高原则

1. **开发必须有提交。** 完成状态不能只存在于聊天记录、共享工作树或临时目录；没有 commit SHA，就不能被视为可发布交付物。
2. **发布不能盲收，也不能静默忽略。** 发布 Agent 不能直接发布未知脏改动，但必须查清它们是已提交副本、遗漏的完成工作，还是未完成或有风险的中间状态。
3. **正式版本只有一个发布负责人。** 普通开发 Agent 不合并、不改版本号、不推 GitHub、不部署；发布 Agent 只在用户明确授权后接管一次版本。

## 2. 角色与责任

### 2.1 开发 Agent

开发 Agent 负责一个边界清晰的功能或修复。

开始前必须：

```bash
git status --short --branch
git worktree list --porcelain
git branch --all --verbose --no-abbrev
```

开发规则：

- 使用唯一分支和独立 worktree，不在共享 `main` 直接开发；
- 记录起始基线 SHA，只修改自己负责的文件；
- 不执行 `git reset --hard`、`git checkout -- <file>`、清空他人 stash 或删除未知 worktree；
- 不使用 `git add -A`、`git add .` 等可能夹带他人改动的命令，必须显式暂存本任务文件；
- 发现与其他 Agent 修改同一逻辑时，停止扩大范围并报告冲突；
- 完成后运行与风险匹配的测试并创建一个或多个本地 commit；
- 不推送远端，不合并到 `main`，不创建 tag，不修改正式版本号，不发布 npm，不部署正式环境；
- 不从维护者 Mac 执行任何 GitHub 写操作。

完成交付必须包含：

```text
分支：<branch>
基线：<base SHA>
提交：<commit SHA，可多个>
改动：<用户可感知变化>
文件：<主要修改范围>
验证：<实际运行并通过的命令>
依赖：<前置提交或无>
遗留：<未验证、风险或无>
发布后验收：<需要在线确认的行为>
```

如果任务还没有提交，必须明确写“未完成交付”，不能只说“代码已经写好”。

### 2.2 发布 Agent

发布 Agent 是某一版本唯一的整合与发布负责人。只有用户明确要求当前 Agent 发版时，才能承担这个角色。

发布 Agent 负责：

- 盘点所有 worktree、分支、候选提交和未提交修改；
- 建立候选提交表并逐 SHA 审查；
- 在独立 release worktree 中合并或 cherry-pick；
- 处理冲突、补充集成测试和必要的发布元数据；
- 更新版本号和中英文版本说明；
- 完成隐私、质量、构建、打包、安装和线上验活；
- 通过专用发布服务器完成 GitHub fetch、候选分支检查、fast-forward push 和远端 SHA 验真；
- 报告纳入、排除、重复和仍待处理的改动。

发布 Agent 不得：

- 把共享工作树整体当作发布输入；
- 因为某项改动没有提交就不调查、不说明地跳过；
- 为了凑齐版本在发布窗口临时扩展业务功能；
- 覆盖其他 Agent 的未提交工作；
- 在服务器失败后改为从 Mac 直推 GitHub；
- 把未验证事项写成已经完成。

### 2.3 验收或产品 Agent

验收 Agent 可以复现问题、定义验收标准和检查线上体验，但不代替开发 Agent 交付提交，也不代替发布 Agent 执行版本发布。详细职责见[任务职责与分工](任务职责与分工.md)。

## 3. 共享工作树规则

共享 `main` 只用于查看、盘点和必要的只读检查，不应成为并行开发目录。

如果发现共享工作树有未提交修改：

1. 立即记录文件列表，不执行覆盖、回滚或清理；
2. 检查所有 worktree 和分支，寻找对应提交；
3. 比较文件内容或补丁，判断是否为已提交任务的重复副本；
4. 查找负责 Agent 的交付信息、测试和依赖；
5. 在归属不清前，不继续在这些文件上叠加修改。

禁止用以下方式“恢复干净”：

```text
git reset --hard
git checkout -- <file>
git restore <unknown-file>
git clean -fd
git stash 后删除或覆盖 stash
```

共享工作树脏状态本身是需要处理的协作事件，不能当作普通噪声。

## 4. 未提交改动的强制分类

发布 Agent 必须把每组未提交修改归入以下一类，并在发布报告中说明。

### A. 已提交任务的重复副本

判断依据可以包括：

- 工作区文件与某个候选提交或 release 分支内容完全一致；
- 补丁与已提交功能等价；
- 对应分支有明确测试和交付记录。

处理方式：

- 发布时使用正式提交 SHA，不使用共享副本；
- 在报告中注明“已通过提交纳入，当前脏文件是重复副本”；
- 发布后再按安全清理流程处理共享副本。

### B. 已完成但遗漏提交

必须同时满足：

- 功能边界清楚；
- 可以识别负责人或修改来源；
- 测试和验收结果可复核；
- 与当前发布基线没有未解决冲突。

处理顺序：

1. 优先要求原开发 Agent 在自己的 worktree 补建提交；
2. 原 Agent 不可用时，发布 Agent 先在独立恢复分支保存补丁；
3. 逐文件审查、运行测试后创建单独恢复提交；
4. 只有形成明确 SHA 后才进入候选表。

不得直接在共享 `main` 上执行 `git add . && git commit`。

### C. 未完成或无法确认

包括：

- 没有测试；
- 只有部分文件；
- 依赖关系不明；
- 同时包含调试内容；
- 无法确认用户可见行为；
- 与其他已发布修复冲突。

处理方式：保留并明确排除，不得发布，也不得描述为“已完成”。

### D. 会覆盖已验证修复的过期版本

例如共享目录中的文件基于旧基线，缺少后来加入的 Windows、审批、生命周期或安全修复。

处理方式：

- 不能整文件覆盖；
- 只允许从中提取仍有价值的独立 hunk；
- 提取后重新运行相关回归测试；
- 在新提交中说明保留了哪些较新的行为。

## 5. 发布前盘点

发布 Agent 开始前至少运行：

```bash
git status --short --branch
git diff --check
git worktree list --porcelain
git branch --all --verbose --no-abbrev
git log --all --oneline --decorate -40
```

随后建立候选表：

| 提交或改动组 | 来源 | 用户变化 | 验证 | 与其他提交关系 | 处理结论 |
| --- | --- | --- | --- | --- | --- |
| SHA / dirty group | branch / worktree | 一句话 | 通过 / 风险 | 独立 / 重复 / 冲突 / 依赖 | 纳入 / 恢复提交 / 排除 |

冻结发布范围前必须回答：

- 所有干净 worktree 的新提交是否都已检查？
- 所有脏 worktree 是否都已分类？
- 是否存在“完成但未提交”的任务？
- 是否存在内容等价但 SHA 不同的 cherry-pick？
- 当前 release 基线是否包含上次已部署的全部修复？

## 6. 正式发布流程

### 6.1 冻结范围

- 确定目标版本和基线；
- 确定纳入的明确提交 SHA；
- 记录排除项和原因；
- HEAD、候选提交或关键配置变化后重新冻结。

### 6.2 独立整合

- 从正确基线创建独立 release worktree；
- 按依赖顺序逐个 cherry-pick 或合并；
- 冲突按功能意图解决，不能用“整文件取最新”代替审查；
- 冲突解决后重跑相关测试；
- 不重写开发 Agent 的分支历史。

### 6.3 版本和说明

只有发布 Agent 可以：

- 更新 `package.json`、锁文件和正式版本号；
- 在 `docs/发布/版本记录/` 新建版本说明；
- 更新[版本索引](../发布/版本记录/版本索引.md)；
- 准备 release commit 和 tag 候选。

正式版由用户明确决定；在此之前使用 `0.x.x`。历史错误编号保留用于追溯，但必须明确标注其预览性质。

### 6.4 完整质量门禁

至少运行：

```bash
git diff --check
npm run privacy:check
npm run lint
npm run typecheck:src
bun test test
npm run build
npm pack --dry-run --json
```

涉及 CLI、daemon、全局安装或正式网页时，还要执行安装、服务重启、真实任务和公网验活。失败必须保留为失败，不能用局部测试替代。

### 6.5 GitHub 和部署

- Mac 只生成经过隐私检查、不含 `.git` 的公开快照；
- GitHub fetch、公开 commit、push、tag 和 `git ls-remote` 验真只能在专用发布服务器完成；
- 公开 commit 必须先进入一次性候选分支，等待 Secret scan 与 Linux、macOS、Windows 全部通过，再把同一 SHA fast-forward 到 `main`；
- `main` 必须保持四项检查的严格分支保护，禁止 force push 和删除；不得为了通过发布临时关闭保护；
- `main` 推送触发的最新一轮四项 CI 也要完成验真，不能只引用候选分支结果；
- 推送必须 fast-forward，拒绝强推和 non-fast-forward；
- 正式 Relay 使用 npm pack 产物部署，保留回滚目录，不影响服务器其他项目；
- 详细操作见[对外发布操作手册](../发布/对外发布操作手册.md)。

### 6.6 发布后验收

至少核对：

- GitHub 远端 SHA；
- 候选分支与 `main` 最新运行的 Secret scan 和三平台 CI，特别是 Windows；
- `main` 分支保护、候选分支清理和未处理 Secret alerts；
- 本机安装版本和健康状态；
- 公网网页、认证 API、Relay 设备在线；
- 任务读取、消息发送和回读；
- 本次涉及的审批、通知、附件或缓存行为；
- 未纳入改动仍被安全保留。

## 7. 发布后清理

发布成功不等于可以立即删除分支和 worktree。

清理顺序：

1. 记录已发布版本、公开 SHA 和本地 release SHA；
2. 将共享脏状态与已发布基线逐文件比较；
3. 对重复副本保存分类证据后再清理；
4. 把独有且有价值的改动迁移到新分支并提交；
5. 确认没有唯一内容后，才删除临时 worktree、过期分支和快照；
6. 不自动删除其他 Agent 仍可能使用的工作区。

发布报告必须区分：

- 已提交且已发布；
- 已提交但未发布；
- 已发布提交的重复脏副本；
- 未完成或无法确认的修改；
- 仍需下一版本处理的独有改动。

## 8. 版本说明写法

中文版本说明是面向用户的主记录，使用[中文版本说明模板](../发布/版本记录/中文版本说明模板.md)。

应该写：

- 用户现在能做什么；
- 之前遇到什么问题，现在如何改善；
- 是否需要重启、登录、重新发送或修改配置；
- 仍存在什么限制。

不应该写：

- 类名、字段名、内部路径和大段提交 SHA；
- “优化若干”“修复问题”等空话；
- 没有实测依据的“彻底解决”“全部支持”；
- 把未发布或未验收的功能写成已经上线。

技术细节和测试证据放在 commit body、候选表和发布验收报告中。

## 9. 快速检查表

### 开发 Agent 完成前

- [ ] 在独立 worktree 和分支工作；
- [ ] 只修改并暂存自己的文件；
- [ ] 测试通过；
- [ ] 已创建 commit；
- [ ] 已报告 SHA、依赖、风险和验收项；
- [ ] 没有推送、发版或部署。

### 发布 Agent 发布前

- [ ] 全部 worktree、分支和 dirty state 已盘点；
- [ ] 每组未提交改动已分类；
- [ ] 完成但未提交的工作已补成独立提交或明确排除；
- [ ] 候选提交表已冻结；
- [ ] release worktree 干净；
- [ ] 完整质量门禁通过；
- [ ] 隐私快照不含 `.git` 和本地状态；
- [ ] 当前快照隐私检查与完整 Git 历史密钥扫描的范围已经区分；
- [ ] `main` 分支保护仍要求 Secret scan 和三平台质量检查。

### 发布 Agent 完成后

- [ ] GitHub SHA、候选 CI、`main` 最新 CI、分支保护和候选分支清理已验真；
- [ ] 纳入与排除项已报告；
- [ ] 共享工作树中的重复、独有和风险改动已分别说明；
- [ ] 没有误删其他 Agent 的工作；
- [ ] 后续清理或补发任务已有明确负责人。
