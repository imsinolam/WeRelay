# WeRelay 多 Agent 协作规范

> 本文是 WeRelay 多 Agent 开发和发布的强制规范。任何 Agent 在修改仓库前都应阅读本文；`AGENTS.md` 负责给出仓库级硬约束，本文负责解释完整协作流程。

WeRelay 允许多个 Agent 同时工作，但代码开发、版本整合和正式发布必须由不同角色按清晰边界完成。目标不是“尽快把当前目录提交掉”，而是保证每一项改动都可追踪、可验证、可回滚，不覆盖其他 Agent，也不遗漏已经完成的任务。

## 1. 三条最高原则

1. **开发必须有提交。** 完成状态不能只存在于聊天记录、共享工作树或临时目录；没有 commit SHA，就不能被视为可发布交付物。
2. **发布不能盲收，也不能静默忽略。** 发布 Agent 不能直接发布未知脏改动，但必须查清它们是已提交副本、遗漏的完成工作，还是未完成或有风险的中间状态。
3. **正式版本只有一个发布负责人。** 普通开发 Agent 不合并、不改版本号、不推 GitHub、不部署；发布 Agent 只在用户明确授权后接管一次版本。

## 2. 角色与责任

### 2.1 开发 Agent

开发 Agent 负责一个边界清晰的功能或修复。

开始前必须：

```bash
git status --short --branch
git worktree list --porcelain
git branch --all --verbose --no-abbrev
```

开发规则：

- 使用唯一分支和独立 worktree，不在共享 `main` 直接开发；
- 记录起始基线 SHA，只修改自己负责的文件；
- 不执行 `git reset --hard`、`git checkout -- <file>`、清空他人 stash 或删除未知 worktree；
- 不使用 `git add -A`、`git add .` 等可能夹带他人改动的命令，必须显式暂存本任务文件；
- 发现与其他 Agent 修改同一逻辑时，停止扩大范围并报告冲突；
- 完成后运行与风险匹配的测试并创建一个或多个本地 commit；
- 不推送远端，不合并到 `main`，不创建 tag，不修改正式版本号，不发布 npm，不部署共享环境；
- 不从维护者 Mac 执行任何 GitHub 写操作。

完成交付必须包含：

```text
分支：<branch>
基线：<base SHA>
提交：<commit SHA，可多个>
改动：<用户可感知变化>
文件：<主要修改范围>
验证：<实际运行并通过的命令>
依赖：<前置提交或无>
遗留：<未验证、风险或无>
体验验收：<需要在本机或公网确认的行为>
```

如果任务还没有提交，必须明确写“未完成交付”，不能只说“代码已经写好”。

### 2.2 体验整合 Agent

体验整合 Agent 是某一候选基线唯一的整合和部署负责人。运行代码提交后默认进入体验部署，不需要用户逐次下达部署指令。开发 Agent 完成 commit 后必须交接给当前体验整合负责人；没有其他负责人时，当前 Agent 可以在完成全仓盘点后接管，但普通开发 Agent 不得直接拿自己的分支并发覆盖服务器。

“默认进入体验部署”是 Agent 的强制收尾职责，不表示 Git 提交会自动触发后台部署。当前任务 Agent 必须确认候选实际完成整合、安装和验活后才能报告部署完成；如果因并发、凭据、服务器或验证失败而停下，必须明确报告“已提交但尚未部署”和阻塞原因。

体验整合 Agent 负责：

- 盘点所有 worktree、分支、候选提交和未提交修改；
- 建立候选提交表并逐 SHA 审查；
- 在独立 release worktree 中合并或 cherry-pick；
- 处理冲突、补充集成测试和必要的候选元数据；
- 使用可追溯的预发布版本打包同一个 tarball；
- 完成隐私、质量、构建、打包、本机安装和线上验活；
- 将同一产物部署到公网 Relay，记录 SHA-256 和回滚产物；
- 报告纳入、排除、重复和仍待处理的改动；
- 在每次候选内容变化后重新验证、部署并重置观察基线；
- 串行处理部署，防止多个 Agent 用不同候选互相覆盖。

体验整合 Agent 不得：

- 执行 GitHub 写操作、创建正式 tag 或宣称正式新版本已经发布；
- 把共享工作树整体当作候选输入；
- 因为某项改动没有提交就不调查、不说明地跳过；
- 为了凑齐候选在整合窗口临时扩展业务功能；
- 覆盖其他 Agent 的未提交工作；
- 把未验证事项写成已经完成。

### 2.3 正式发布 Agent

正式发布 Agent 是某一 GitHub 版本唯一的公开发布负责人。只有用户明确要求“发布 GitHub 新版本”等等价动作后，才能承担这个角色。

正式发布 Agent 负责：

- 锁定用户确认、已经完成体验验收的最后一个候选基线；
- 确认候选之后的新提交没有被静默夹带；
- 将预发布版本收敛为正式 `0.x.x`，更新中英文版本说明；
- 重新运行完整门禁并生成正式 tarball；
- 验证正式文件树与体验通过的候选一致，差异仅限版本和发布元数据；
- 通过专用发布服务器完成 GitHub fetch、候选分支检查、fast-forward push、tag 和远端 SHA 验真；
- 用同一正式 tarball 更新本机和公网 Relay，并再次完成线上验活。

正式发布 Agent 不得：

- 把未经过体验部署和观察的新提交直接加入正式版本；
- 在候选已变化时继续沿用旧验收结论；
- 在发布服务器失败后改为从 Mac 直推 GitHub；
- 为通过 CI 临时关闭分支保护、强推或删除 `main`。

### 2.4 验收或产品 Agent

验收 Agent 可以复现问题、定义验收标准和检查线上体验，但不代替开发 Agent 交付提交，也不代替体验整合 Agent 或正式发布 Agent 执行其专属动作。详细职责见[任务职责与分工](任务职责与分工.md)。

## 3. 共享工作树规则

共享 `main` 只用于查看、盘点和必要的只读检查，不应成为并行开发目录。

如果发现共享工作树有未提交修改：

1. 立即记录文件列表，不执行覆盖、回滚或清理；
2. 检查所有 worktree 和分支，寻找对应提交；
3. 比较文件内容或补丁，判断是否为已提交任务的重复副本；
4. 查找负责 Agent 的交付信息、测试和依赖；
5. 在归属不清前，不继续在这些文件上叠加修改。

禁止用以下方式“恢复干净”：

```text
git reset --hard
git checkout -- <file>
git restore <unknown-file>
git clean -fd
git stash 后删除或覆盖 stash
```

共享工作树脏状态本身是需要处理的协作事件，不能当作普通噪声。

## 4. 未提交改动的强制分类

发布 Agent 必须把每组未提交修改归入以下一类，并在发布报告中说明。

### A. 已提交任务的重复副本

判断依据可以包括：

- 工作区文件与某个候选提交或 release 分支内容完全一致；
- 补丁与已提交功能等价；
- 对应分支有明确测试和交付记录。

处理方式：

- 发布时使用正式提交 SHA，不使用共享副本；
- 在报告中注明“已通过提交纳入，当前脏文件是重复副本”；
- 发布后再按安全清理流程处理共享副本。

### B. 已完成但遗漏提交

必须同时满足：

- 功能边界清楚；
- 可以识别负责人或修改来源；
- 测试和验收结果可复核；
- 与当前发布基线没有未解决冲突。

处理顺序：

1. 优先要求原开发 Agent 在自己的 worktree 补建提交；
2. 原 Agent 不可用时，发布 Agent 先在独立恢复分支保存补丁；
3. 逐文件审查、运行测试后创建单独恢复提交；
4. 只有形成明确 SHA 后才进入候选表。

不得直接在共享 `main` 上执行 `git add . && git commit`。

### C. 未完成或无法确认

包括：

- 没有测试；
- 只有部分文件；
- 依赖关系不明；
- 同时包含调试内容；
- 无法确认用户可见行为；
- 与其他已发布修复冲突。

处理方式：保留并明确排除，不得发布，也不得描述为“已完成”。

### D. 会覆盖已验证修复的过期版本

例如共享目录中的文件基于旧基线，缺少后来加入的 Windows、审批、生命周期或安全修复。

处理方式：

- 不能整文件覆盖；
- 只允许从中提取仍有价值的独立 hunk；
- 提取后重新运行相关回归测试；
- 在新提交中说明保留了哪些较新的行为。

## 5. 整合或正式发布前盘点

体验整合 Agent 或正式发布 Agent 开始前至少运行：

```bash
git status --short --branch
git diff --check
git worktree list --porcelain
git branch --all --verbose --no-abbrev
git log --all --oneline --decorate -40
```

随后建立候选表：

| 提交或改动组 | 来源 | 用户变化 | 验证 | 与其他提交关系 | 处理结论 |
| --- | --- | --- | --- | --- | --- |
| SHA / dirty group | branch / worktree | 一句话 | 通过 / 风险 | 独立 / 重复 / 冲突 / 依赖 | 纳入 / 恢复提交 / 排除 |

冻结候选或正式发布范围前必须回答：

- 所有干净 worktree 的新提交是否都已检查？
- 所有脏 worktree 是否都已分类？
- 是否存在“完成但未提交”的任务？
- 是否存在内容等价但 SHA 不同的 cherry-pick？
- 当前 release 基线是否包含上次已部署的全部修复？

## 6. 两阶段交付流程

完整流程见[体验部署与正式发布](../发布/体验部署与正式发布.md)。体验部署与 GitHub 正式发布是两个独立阶段，不能用一次“发版”含糊代替。

### 6.1 冻结候选范围

- 确定当前公开正式版和下一候选版本；
- 确定纳入的明确提交 SHA；
- 记录排除项和原因；
- HEAD、候选提交、打包内容或关键配置变化后重新冻结；
- 不把共享工作树的未提交内容直接纳入候选。

### 6.2 独立整合

- 从正确基线创建独立 release worktree；
- 按依赖顺序逐个 cherry-pick 或合并；
- 冲突按功能意图解决，不能用“整文件取最新”代替审查；
- 冲突解决后重跑相关测试；
- 不重写开发 Agent 的分支历史。

### 6.3 第一阶段：体验候选部署

运行代码形成 commit 后自动触发本阶段，不需要用户再次说“发布”或“部署”。体验整合 Agent 使用预发布版本，例如 `0.3.5-preview.20260826.1`，并记录候选 Git SHA、纳入提交、tarball 文件名、SHA-256、部署位置、部署时间、验活结果和回滚产物。纯文档、测试说明或 CI 维护没有改变运行产物时，只记录到下一候选清单，不为此单独重启服务。

体验候选必须：

- 完成完整质量门禁；
- 使用实际 `npm pack` 产物，而不是直接复制源码覆盖服务；
- 用同一 tarball 完成本机安装和公网 Relay 部署；
- 验证本机服务、网页、API、设备在线、任务读取、消息发送和本次专项行为；
- 保留上一个稳定 tarball 和安全回滚步骤；
- 明确报告“GitHub 尚未发布”；
- 不创建正式 tag，不执行 GitHub 写操作。

**体验部署不是 GitHub 正式发布。** 服务器在观察期内可以暂时领先 GitHub，但运行版本必须可由候选 SHA 和 tarball 校验值复现。

### 6.4 观察与修复

观察期由用户决定，不设固定天数。发现问题时可以先回滚运行服务，但必须保留失败候选的 Git 提交和证据。修复应在独立分支形成新 commit，再由体验整合 Agent 重新整合、验证、打包和部署。

只要源码、配置模板或打包内容变化，就必须产生新的候选标识，并从最新成功部署重新开始观察。旧候选的自动测试和体验结论不能直接覆盖新文件树。

### 6.5 第二阶段：GitHub 正式发布

只有用户明确要求发布 GitHub 新版本，正式发布 Agent 才能开始：

- 正式发布只能基于已经完成体验验收的候选基线；
- 新提交不得未经体验直接加入正式版本；
- 将预发布版本收敛为正式 `0.x.x`，更新锁文件和中英文版本说明；
- 重新运行完整质量门禁并生成正式 tarball；
- 除正式版本、版本说明和由此产生的构建元数据外，正式文件树必须与体验通过的候选一致；
- Mac 只生成经过隐私检查、不含 `.git` 的公开快照；
- GitHub fetch、公开 commit、push、tag 和 `git ls-remote` 验真只能在专用发布服务器完成；
- 公开 commit 必须先进入一次性候选分支，等待 Secret scan 与 Linux、macOS、Windows 全部通过，再把同一 SHA fast-forward 到 `main`；
- `main` 必须保持四项检查的严格分支保护，禁止 force push 和删除；不得为了通过发布临时关闭保护；
- `main` 推送触发的最新一轮四项 CI 也要完成验真，不能只引用候选分支结果；
- 推送必须 fast-forward，拒绝强推和 non-fast-forward；
- 最终使用同一正式 tarball 更新本机和公网 Relay，再次验活并保留回滚目录；
- 详细 GitHub 操作见[对外发布操作手册](../发布/对外发布操作手册.md)。

### 6.6 完整质量门禁

体验候选和 GitHub 正式发布至少都运行：

```bash
git diff --check
npm run privacy:check
npm run lint
npm run typecheck:src
bun test test
npm run build
npm pack --dry-run --json
```

涉及 CLI、daemon、全局安装或正式网页时，还要执行实际 tarball 安装、服务重启、真实任务和公网验活。失败必须保留为失败，不能用局部测试或旧候选结果替代。

### 6.7 正式发布后验收

至少核对：

- GitHub 远端 SHA；
- 候选分支与 `main` 最新运行的 Secret scan 和三平台 CI，特别是 Windows；
- `main` 分支保护、候选分支清理和未处理 Secret alerts；
- 本机安装版本和健康状态；
- 公网网页、认证 API、Relay 设备在线；
- 任务读取、消息发送和回读；
- 本次涉及的审批、通知、附件或缓存行为；
- 未纳入改动仍被安全保留；
- 正式服务器安装的 tarball 与 GitHub 正式文件树一致。

## 7. 发布后清理

发布成功不等于可以立即删除分支和 worktree。

清理顺序：

1. 记录已发布版本、公开 SHA 和本地 release SHA；
2. 将共享脏状态与已发布基线逐文件比较；
3. 对重复副本保存分类证据后再清理；
4. 把独有且有价值的改动迁移到新分支并提交；
5. 确认没有唯一内容后，才删除临时 worktree、过期分支和快照；
6. 不自动删除其他 Agent 仍可能使用的工作区。

发布报告必须区分：

- 已提交且已发布；
- 已提交但未发布；
- 已发布提交的重复脏副本；
- 未完成或无法确认的修改；
- 仍需下一版本处理的独有改动。

## 8. 版本说明写法

中文版本说明是面向用户的主记录，使用[中文版本说明模板](../发布/版本记录/中文版本说明模板.md)。

应该写：

- 用户现在能做什么；
- 之前遇到什么问题，现在如何改善；
- 是否需要重启、登录、重新发送或修改配置；
- 仍存在什么限制。

不应该写：

- 类名、字段名、内部路径和大段提交 SHA；
- “优化若干”“修复问题”等空话；
- 没有实测依据的“彻底解决”“全部支持”；
- 把未发布或未验收的功能写成已经上线。

技术细节和测试证据放在 commit body、候选表和发布验收报告中。

## 9. 快速检查表

### 开发 Agent 完成前

- [ ] 在独立 worktree 和分支工作；
- [ ] 只修改并暂存自己的文件；
- [ ] 测试通过；
- [ ] 已创建 commit；
- [ ] 已报告 SHA、依赖、风险和体验验收项；
- [ ] 运行代码提交已交接给唯一体验整合负责人；
- [ ] 没有推送 GitHub，也没有并发直接覆盖服务器。

### 体验整合 Agent 部署前

- [ ] 全部 worktree、分支和 dirty state 已盘点；
- [ ] 每组未提交改动已分类；
- [ ] 完成但未提交的工作已补成独立提交或明确排除；
- [ ] 候选提交表和预发布版本已冻结；
- [ ] release worktree 干净；
- [ ] 完整质量门禁通过；
- [ ] 实际 tarball 的文件名和 SHA-256 已记录；
- [ ] 上一个稳定产物和回滚步骤可用。

### 体验整合 Agent 部署后

- [ ] 本机与公网 Relay 安装的是同一 tarball；
- [ ] 服务、网页、API、设备在线和真实消息链路已验活；
- [ ] 纳入与排除项已报告；
- [ ] 已明确说明 GitHub 尚未发布；
- [ ] 共享工作树中的重复、独有和风险改动已分别说明；
- [ ] 没有误删其他 Agent 的工作。

### 正式发布 Agent GitHub 发布前

- [ ] 用户已明确要求发布 GitHub 新版本；
- [ ] 已锁定最后一个体验通过的候选 SHA 和 tarball 校验值；
- [ ] 新提交没有未经体验被夹带；
- [ ] 正式文件树与体验候选一致；
- [ ] 完整质量门禁已重新通过；
- [ ] 隐私快照不含 `.git` 和本地状态；
- [ ] 当前快照隐私检查与完整 Git 历史密钥扫描的范围已经区分；
- [ ] `main` 分支保护仍要求 Secret scan 和三平台质量检查。

### 正式发布 Agent 完成后

- [ ] GitHub SHA、候选 CI、`main` 最新 CI、分支保护和候选分支清理已验真；
- [ ] 本机与公网服务器已安装同一正式 tarball；
- [ ] GitHub、版本说明、安装产物和运行版本一致；
- [ ] 后续清理或补发任务已有明确负责人。
