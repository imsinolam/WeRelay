# ClawBot 积压通知：只随任务列表提醒一次

## 用户可见规则

- 用户主动获取任务列表（“任务”、终端筛选、搜索或翻页）且列表和使用说明完整送达后，如有尚未提醒的积压，附带一条合并提醒。
- 同一条积压只提醒一次。再次获取列表、其他积压过期导致数量减少、网络恢复和程序重启，都不能重复提醒已提醒的内容。
- 新增积压等用户下一次获取列表再提醒；后台恢复和普通聊天不主动弹出积压提醒。
- 提醒失败不算提醒成功，不后台重试；等下一次用户获取列表再尝试。列表发送失败或只发出一部分时不附带提醒。
- 用户明确回复“推送”或“补发”，才补发较早的结果；仅提醒过并不等于结果已送达。

本次保留现有时间窗口：3 分钟内完成的仍按正常通知策略投递，3 分钟至 1 小时属于待确认积压，超过 1 小时停止补发。审批队列、屏幕状态节流及子任务完成静默规则不变。

实现与上线边界补充：0.3.20 只移植了积压提醒修复，并未包含原依赖的子任务来源过滤；不能据本文旧交付说明判定运行包已具备该能力。来源过滤及列表隐藏统一见[内部子任务与通知规则](内部子任务与通知规则.md)，部署后必须同时核验这两组行为。

## 根因与实现边界

旧逻辑在后台恢复中按整批通知 key 的指纹去重，且仅存内存。积压从 4 条过期减至 3 条，会生成不同指纹并再发一次；重启也会丢失去重。

现在每条 pending 记录保存 `backlogNotifiedAt`，经现有私有原子状态文件持久化；只有微信发送成功才标记。它不推进正文发送位置、不写 delivered、不清正文缓存；记录随队列生命周期清理，不新建无限增长的提醒 key 集合。

唯一提醒入口是 `queueWechatTaskListMessage` 完整发送后的 `remindClawbotBacklogAfterTaskList`。后台恢复仅保留正常近期通知与过期清理。提醒使用单飞防止并发列表重复发送，共享失败也不能把已成功发送的列表误报为失败；来源读取失败仍保留 pending。

后续不得将提醒放回 token 刷新、轮询恢复或启动排空路径，也不得用“剩余积压数量变化”重置已提醒状态。完成通知来源过滤继续复用共用策略，子任务完成不混入提醒，子任务审批保持独立。
